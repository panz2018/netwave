## 过期检查门禁化（`check:outdated` 要不要进 CI 门禁，待拍板）

**人工观点（支持进）**：把 `pnpm check:outdated` 设成 `ci.yml` 门禁，发现
过时直接报错，就能保证永远使用最新版，以后不需要人工手动升级。

**agent 观点（反对做成每 PR 门禁）**，四条理由：

1. **不可复现**：同一 commit 今天绿、明天上游发新版就红。作者没碰依赖却被
   拦，评审者无法判断 PR 本身好坏——"CI 红 = 你这个 PR 弄坏了什么"被破坏。
2. **网络抖动 = CI 抖动**：脚本要连 GitHub API / npm registry / endoflife.date
   三家，匿名限流 60 次/小时，任何一家抽风全仓 PR 陪葬。
3. **与已定选线策略打架**：dependency-upgrade spec 明确"不追 current 线、
   Python 等新 minor 且所需库全部支持才切"。若"过时即红"，Python 3.15 发布
   当天所有 PR 全红，逼人在库支持未验证时升级——违反「运行时大版本升级流程」。
4. **"永远最新"不是本仓目标**：目标是"最新稳定线 + 可复现"；追新带来的配置
   churn 正是选线原则要防的。

**折中方案（agent 建议，待人工确认）**：定时任务而非 PR 门禁——每周 cron 跑
`check:outdated`，发现 LAG 自动开 issue（或自动开 lockfile 刷新 PR）。lockfile
minor/patch 属「升级分级」中的例行刷新，机器人可代办；大版本升级涉及库支持
矩阵 + 四端对拍，MUST 走 OpenSpec change，机器人替代不了人。

**安全阀（门禁化 change 的备查要求）**：任何自动化提议升级（机器人开 issue /
刷新 PR）MUST NOT 推荐 `scripts/versions/restrictions.json` 已登记的版本——
由 `check_outdated.py` 统一消费（契约见 dependency-upgrade spec），门禁化
实现时直接复用其过滤结果，禁止另造第二套判断。

**落地形态**：改动触及契约——「过期体检命令」的 MUST NOT 进 CI 条款（改为
"定时可进、PR 门禁不进"）、新增 workflow——属结构性升级，MUST 单独开
OpenSpec change（暂名 `add-freshness-schedule-gate`），待拍板后 propose。

## 归档目录分层（`openspec/changes/archive/` 要不要按年/月分桶，待拍板）

**问题**：归档目录现有 35 个 change 文件夹平铺，每次打开是一长串，找单个
change 靠肉眼扫。按月统计现有分布：2026-09 共 7 个、2026-10 共 23 个、
2026-11 共 5 个——单月最多 23 个，确实到了平铺难看的量级。

**候选布局**：

- A. 年/月两级：`archive/2026-10/<date>-<name>/`——单目录最多 23 个，
  随年份增长不恶化
- B. 只年级：`archive/2026/<date>-<name>/`——本仓全部归档都在同一年，
  今年零收益，明年才起作用
- C. 不分层：目录名已带 `YYYY-MM-DD` 前缀，排序天然按时间有序，
  "一大堆"只是编辑器列目录的观感问题

**已核实的落地障碍**（决定这不是单纯 `mv`）：

1. **openspec CLI 不支持自定义归档布局**：`openspec archive --help` 只有
   `-y` / `--skip-specs` / `--no-validate` / `--json` / `--store`，
   无归档目录参数；`openspec config list` 亦无布局项。CLI 每次都会把 change
   平铺写进 `archive/`，分层只能靠归档**之后**再 `mv`，或包一层脚本
   （`archive` + `mv` + 校验）——漏跑 `mv` 就会出现新旧两种布局并存。
2. **门禁正则会静默失效**：`scripts/check_md.py` 的 ARCHIVE PATH 规则用
   `openspec/changes/archive/([A-Za-z0-9._-]+)/?` 只认**一段**目录名，
   分层后 `archive/2026-10/<name>/` 形态不匹配——不报错，而是**不再校验**，
   失效是静默的，必须同步改正则。
3. **治理 spec 有对应条款**：`openspec/specs/project-governance/spec.md`
   「归档指针指向不存在目录即红」等 Scenario 以单段 `<name>` 形态表述，
   分层属契约变更，MUST 走 OpenSpec change 改措辞。
4. **存量引用需随迁移更新**：全仓行内路径引用现有 1 处
   （`Plan/总体计划.md` 指向 `archive/2026-09-27-monorepo-scaffold/`）；
   另外归档目录本身是冻结历史，迁移会改动其在 git 中的路径，
   旧提交信息/旧 PR 里提到的旧路径不再存在（内容不改，追溯靠 git log）。

**agent 建议**：先不急着分层，理由与前置条件——

- 分层收益是编辑器观感与人工翻找便利，**没有任何机器流程依赖归档布局**
  （闸门、spec、CI 都只读 `openspec/specs/`，不读 archive）；
- 代价是每次归档多一步、且这一步漏跑就破坏一致性（障碍 1），
  属于"新增人工仪式"，与最小规则原则相悖；
- 若仍要做，推荐 **A（年/月两级）+ 包装脚本**：把 `archive` + `mv` +
  `pnpm check:md` 封成一条命令（例如 `scripts/archive_change.sh`），
  让人只跑一条、机器保证不漏 `mv`；同轮改正则与治理 spec 措辞，
  并把存量 35 个目录一次性迁入各自年月桶。
- 若只想解决观感，C 是零成本选项：不改仓库结构，靠目录名日期前缀排序即可。

**落地形态**：选 A/B 即触及契约（治理 spec 归档路径条款 + `check_md.py`
正则 + 新增包装脚本 + 存量迁移），MUST 单独开 OpenSpec change
（暂名 `add-archive-date-buckets`）；选 C 则本节点名关闭，不留待办。

## Python 3.15 + pyo3 0.30 升级（暂缓，待治理机制拍板后开 change）

> 原为 OpenSpec change `upgrade-python-3-15`（暂停中），已撤销。升级本身是
> `dependency-upgrade` spec 流程的执行任务，但所依赖的治理机制尚未拍板，
> 机制未定则升级无法有效执行——按 Plan/ 生命周期，未执行的待办回归本档，
> 待机制拍板后另开 change 实战。

**触发条件（已满足）**：Python 3.15 已是稳定版，本项目所需库全部声明支持
（numpy、pyo3、maturin、pytest、ruff、scikit-rf）。按选线原则（单线运行时
取最新稳定 minor）应升 3.15；pyo3 0.30 含 breaking changes，属结构性升级。

**为何暂缓**：过期检查门禁化未拍板（无机器判定）；登记表分工已由退役定案
（`retire-pin-registry`）。

**恢复前置**：① 过期检查门禁化拍板；② oracle uv 环境实际建成
（原 tasks 假设其已存在可"重建"，实为尚未建成）。

**升级范围（恢复时执行）**：

- 运行时 3.14→3.15：`python/.python-version`、CI python 矩阵最新格
  3.14→3.15（底线 3.10 不变）。
- pyo3 0.29→0.30、numpy 同 major 联动、pyo3-stub-gen 升至配套版本；
  breaking changes 以编译报错驱动逐项适配（`FromPyObject` 默认不再生成、
  abi3 feature 逻辑、`PyBuffer` 弃用方法等）。
- abi3 维持 `abi3-py310`、`requires-python` 维持 `>=3.10`（底线不动，
  一个 wheel 覆盖 3.10–3.15）。
- oracle 环境（skrf）在 3.15 下重建 lock，golden 与 3.14 结果应 bit 级一致。
- 文档同步：workspace-layout/ci-matrix 中 "3.14" 措辞随单源化结果核对，
  散文不复制数字。

**执行顺序（恢复时）**：全局 CLI 体检 → 本地 uv 装 3.15 + 升 pyo3/numpy/
stub-gen + 编译报错适配 + `maturin develop` + pytest 全绿 → 依赖刷新
（`uv lock --upgrade`、oracle lock 重建）→ 配置（`.python-version`、
CI 矩阵）→ `pnpm check` 全绿 + `pnpm check:cross` 四端对拍（容差不变）→
grep 全仓 `3.14` 残留清除 → retro 回写 lessons-learned。先本地验证再动 CI
（LL-004 禁止 push-and-pray）。回滚 = `git revert`（版本钉全在钉版文件）。

**不做**：不抬 Python 底线、不切 abi3-py315、不动 Node 矩阵、不采纳 pyo3
新特性（只兼容迁移）、不改任何数值行为与容差。

**落地形态**：治理机制拍板后，按 `dependency-upgrade` spec 升级流程另开
OpenSpec change（`skip_specs`，纯执行；若发现主 spec 残留数字当场补 delta）。
