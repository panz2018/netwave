## blocked 落地（待人工核准）

**首个真实实例：typescript 7.0.0**（升级时坏、7.0.1 起修复）。

- **仓库可核证据**：git `3c6c438`（2026-09-29）记录 "tsdown dts x TS7
  incompatibility with typescript@6 fallback (verified)"——TS 7 初版与
  tsdown dts 管线不兼容，当时降级 `typescript@6` 兜底；原登记表
  `verified` 字段记 "TS 7.0.2 x tsdown dts retested green"，
  7.0.2 复测通过后升回。
- **出处标注**：「7.0.0 坏、7.0.1 起修复」的补丁级细节为人工回忆，
  git log 与 lessons-learned 账本均无补丁级记录（账本 LL-034 是
  tsdown 双 glue 构建顺序坑，非本坏版本）；实施 blocked 机制时若需
  精确补丁号，以 TS releases 为准补核。
- **当时降级取值**：`typescript@6`（`typescript/package.json`
  devDependencies，见 git `3c6c438`）。

**机制实施范围**（spec 条款已由 `retire-pin-registry` 落定，机制代码未实现）：

1. 数据文件：blocked 清单（坏版本 + 原因 + 跟踪 issue），数据出现时创建；
2. 闸门消费：`check_versions.py` 断言当前钉版不落在 blocked 集合；
3. 体检消费：`check_outdated.py` 的 target 跳过 blocked 版本、取相邻
   较低稳定版；
4. spec 条款：「坏版本降级与 blocked 触发式实施」已在
   `dependency-upgrade` spec（随 `retire-pin-registry` 归档生效）；
5. 带出处强制：每条 blocked 记录 MUST 附原因与出处（issue 链接或
   git commit），无出处不登记。

**验收要求**：TDD 先 red——夹具造"钉版命中 blocked"断言闸门 FAIL，
再实现使其 green。

**边界**：本 change（`retire-pin-registry`）只记录实例与实施范围；
机制实现等人工核准后另开 change。

## pairs JSON 化（待触发）

当前载体是 `dependency-upgrade` spec「升级流程固定顺序」的散文（配对

写成一行数据。与 blocked 是两个独立待触发项，禁止绑定同次 change 实施
（spec「blocked 与 pairs 不绑定」Scenario）。

**已核实可填的边**（研究全文见 git log，原「配对版本校验」节随
`retire-pin-registry` 吸收删除）：

- MSRV ≤ toolchain pin（`le`，四律第 1 律已机器覆盖）
- python runtime ≥ `requires-python` 底线（`ge`）
- CI python / node 矩阵格 ≥ 各自底线（`ge`）
- `@napi-rs/cli` ↔ `napi` crate 同 major（`eq_major`）
- pyo3 ↔ numpy 同 major（`eq_major`）
- typescript ↔ tsdown：peer 范围由 `pnpm peers check` 现成闸门覆盖，不重复建

## 过期检查门禁化（`check:outdated` 要不要进 CI 门禁，待拍板）

**人工观点（支持进）**：把 `pnpm check:outdated` 设成 `ci.yml` 门禁，发现
过时直接报错，就能保证永远使用最新版，以后不需要人工手动升级。

**agent 观点（反对做成每 PR 门禁）**，四条理由：

1. **不可复现**：同一 commit 今天绿、明天上游发新版就红。作者没碰依赖却被
   拦，评审者无法判断 PR 本身好坏——"CI 红 = 你这个 PR 弄坏了什么"被破坏。
2. **网络抖动 = CI 抖动**：脚本要连 GitHub API / npm registry / endoflife.date
   三家，匿名限流 60 次/小时，任何一家抽风全仓 PR 陪葬。
3. **与已定选线策略打架**：dependency-upgrade spec 明确"不追 current 线、
   Python 等新 minor 且所需库全部支持才切"。若"过时即红"，Python 3.15 发布
   当天所有 PR 全红，逼人在库支持未验证时升级——违反「运行时大版本升级流程」。
4. **"永远最新"不是本仓目标**：目标是"最新稳定线 + 可复现"；追新带来的配置
   churn 正是选线原则要防的。

**折中方案（agent 建议，待人工确认）**：定时任务而非 PR 门禁——每周 cron 跑
`check:outdated`，发现 LAG 自动开 issue（或自动开 lockfile 刷新 PR）。lockfile
minor/patch 属「升级分级」中的例行刷新，机器人可代办；大版本升级涉及库支持
矩阵 + 四端对拍，MUST 走 OpenSpec change，机器人替代不了人。

**安全阀（门禁化 change 的备查要求）**：任何自动化提议升级（机器人开 issue /
刷新 PR）MUST NOT 推荐 blocked 清单中的版本——坏版本机制落地后由
`check_outdated.py` 统一消费（机制实施范围见本文「blocked 落地」节与
dependency-upgrade spec 触发条款），门禁化实现时直接复用其过滤结果，
禁止另造第二套判断。

**落地形态**：改动触及契约——「过期体检命令」的 MUST NOT 进 CI 条款（改为
"定时可进、PR 门禁不进"）、新增 workflow——属结构性升级，MUST 单独开
OpenSpec change（暂名 `add-freshness-schedule-gate`），待拍板后 propose。

## scripts/ 治理待议（单测覆盖率 / 目录命名 / 脚本自身升级）

`scripts/` 现在有 10 个平铺 py 闸门 + 2 个 sh 安装脚本 + `versions/` 包，
规则驱动改造后闸门域复杂度又上一台阶。三个关联问题尚未拍板，将来专门
讨论后按结论开 OpenSpec change。本节只存正反双方论点与待决点，不预设结论。
已拍板不再讨论：独立 uv 工程——仓库根 `pyproject.toml`（private，
dev 组 pytest/pytest-cov/ruff）已建，契约见
[workspace-layout 根级 Python 工具环境](../openspec/specs/workspace-layout/spec.md)。

### 要不要单元测试 + 覆盖率 100%

**正方（要，且 100%）**：

- 闸门 bug 的后果是**静默放行**（该 FAIL 的输入被放过），比业务代码 bug
  更隐蔽——业务代码错了测试会红，闸门错了没人知道它没拦；
- 闸门是"守门员"，守门员自己没测试体系（无 pytest、无覆盖率），
  与 `python/` 工程的待遇不对等；
- 铁律七本来就要求全端 100% 行覆盖 unit 层零豁免，闸门脚本是仓库代码，
  没有理由例外；
- 四律判定、精确版本正则、markdown 链接/slug 规则、版本比较这些纯逻辑
  分支多，手工 red/green 验证（四律改造即如此）不可回归，改一次闸门就
  得手测一轮。

**反方（要测试，但 100% 一刀切不对）**：

- 脚本里大量代码是**网络与子进程胶水**（`_req`、`run`、GitHub/npm/
  endoflife 三家 API、pnpm/cargo/uv 子进程），逐行覆盖它们只能靠打桩，
  桩测出来的"绿"不证明真环境能跑，反而制造虚假安全感；
- 覆盖率数字对这类工具意义有限：真正危险的是**规则漏判**（该拦没拦），
  这是用例设计问题，不是行覆盖率问题；
- 铁律七的豁免机制（结构性不可达逐条标注）本就为此设计，硬凑 100%
  会催生无断言的"刷覆盖"测试。

**折中（agent 建议，待人工确认）**：纯逻辑（精确版本正则、四律判定、
发现式扫描、markdown 链接/slug 规则、`_semver` 比较、bench/coverage
阈值判定）100% 行覆盖 + 关键分支用例；网络/子进程胶水段打桩测"调用形状"，
异常分支按铁律七逐条 `# pragma: no cover` 标注豁免，禁止整文件排除。

**待决点**：pytest 挂进哪条闸门（`check:py` 追加、还是新命令
`check:scripts`）；进不进 `check:meta`；覆盖率是否进 coverage_gate。

### 目录命名（scripts / manage / control）

**正方（改名 manage/ 或 control/）**：

- "scripts" 太泛，不表达"治理工具集"的身份；manage/control 更点题。

**反方（留 scripts/）**：

- `scripts/` 被钉死在：根 `package.json` 全部命令、`ci.yml`、
  AGENTS/CONTRIBUTING/scripts README、workspace-layout spec、
  install 脚本互引——改名波及面全仓，收益只有"好看"；
- "管理入口"职责已有归属：根 `package.json` 的 `check:*`/`fix:*` 就是
  门面，AGENTS.md 明文"对称命令以根 package.json 为唯一定义处"；
  再造 `manage.py` 调度器 = 第二个命令真相源，必漂移（违反 spec
  唯一真相源原则的同款理由）；
- 命名是名字不是契约，位置语义靠 README 表达即可。

**待决点**：无强烈改名动机，倾向维持；若改，必须与结构收编合并成一次
结构性 change，禁止单独折腾。

### 脚本自身的升级管理

**现状（反方认为无需新机制）**：脚本升级 = 改代码本身，走现有闸门 + git
即可；脚本依赖的外部工具版本（ruff/pytest）由根 `uv.lock` 管，
`check:outdated` 已覆盖；脚本调用的上游工具链由 dependency-upgrade spec
全套机制管。没有缺口。

**正方（仍有可议空间）**：闸门之间有无执行顺序依赖（如 check:meta 内
六闸门顺序）是否需要显式声明与对账；脚本内硬编码的 URL/正则（如
endoflife cycle、npm dist-tag）有无"过期"概念需要体检。

**待决：scripts 覆盖率阈值是否进 coverage_gate**：versions 域补测已完成
（change `add-versions-domain-tests`，覆盖率报数见其 tasks.md 完成记录：
lib 全 100%，仅剩两行 `__main__` 守卫），阈值与范围（仅 `lib/` 还是含
门面/全 scripts）仍未拍板，待另议；在此之前维持"先 `--cov` 报数"。

## Python 3.15 + pyo3 0.30 升级（暂缓，待治理机制拍板后开 change）

> 原为 OpenSpec change `upgrade-python-3-15`（暂停中），已撤销。升级本身是
> `dependency-upgrade` spec 流程的执行任务，但所依赖的治理机制尚未拍板，
> 机制未定则升级无法有效执行——按 Plan/ 生命周期，未执行的待办回归本档，
> 待机制拍板后另开 change 实战。

**触发条件（已满足）**：Python 3.15 已是稳定版，本项目所需库全部声明支持
（numpy、pyo3、maturin、pytest、ruff、scikit-rf）。按选线原则（单线运行时
取最新稳定 minor）应升 3.15；pyo3 0.30 含 breaking changes，属结构性升级。

**为何暂缓**：治理机制未拍板——过期检查门禁化无机器判定、配对校验未落地
（pairs 待触发）、blocked 机制未实施；登记表分工已由退役定案
（`retire-pin-registry`）。机制没落地就升级，等于在没有兜底的情况下做
首次实战。

**恢复前置**：① 上述治理机制拍板并落成闸门规则；② oracle uv 环境实际建成
（原 tasks 假设其已存在可"重建"，实为尚未建成）。

**升级范围（恢复时执行）**：

- 运行时 3.14→3.15：`python/.python-version`、CI python 矩阵最新格
  3.14→3.15（底线 3.10 不变）。
- pyo3 0.29→0.30、numpy 同 major 联动、pyo3-stub-gen 升至配套版本；
  breaking changes 以编译报错驱动逐项适配（`FromPyObject` 默认不再生成、
  abi3 feature 逻辑、`PyBuffer` 弃用方法等）。
- abi3 维持 `abi3-py310`、`requires-python` 维持 `>=3.10`（底线不动，
  一个 wheel 覆盖 3.10–3.15）。
- oracle 环境（skrf）在 3.15 下重建 lock，golden 与 3.14 结果应 bit 级一致。
- 文档同步：workspace-layout/ci-matrix 中 "3.14" 措辞随单源化结果核对，
  散文不复制数字。

**执行顺序（恢复时）**：全局 CLI 体检 → 本地 uv 装 3.15 + 升 pyo3/numpy/
stub-gen + 编译报错适配 + `maturin develop` + pytest 全绿 → 依赖刷新
（`uv lock --upgrade`、oracle lock 重建）→ 配置（`.python-version`、
CI 矩阵）→ `pnpm check` 全绿 + `pnpm check:cross` 四端对拍（容差不变）→
grep 全仓 `3.14` 残留清除 → retro 回写 lessons-learned。先本地验证再动 CI
（LL-004 禁止 push-and-pray）。回滚 = `git revert`（版本钉全在钉版文件）。

**不做**：不抬 Python 底线、不切 abi3-py315、不动 Node 矩阵、不采纳 pyo3
新特性（只兼容迁移）、不改任何数值行为与容差。

**落地形态**：治理机制拍板后，按 `dependency-upgrade` spec 升级流程另开
OpenSpec change（`skip_specs`，纯执行；若发现主 spec 残留数字当场补 delta）。
