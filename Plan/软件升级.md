## 过期检查门禁化（`check:outdated` 要不要进 CI 门禁，待拍板）

**人工观点（支持进）**：把 `pnpm check:outdated` 设成 `ci.yml` 门禁，发现
过时直接报错，就能保证永远使用最新版，以后不需要人工手动升级。

**agent 观点（反对做成每 PR 门禁）**，四条理由：

1. **不可复现**：同一 commit 今天绿、明天上游发新版就红。作者没碰依赖却被
   拦，评审者无法判断 PR 本身好坏——"CI 红 = 你这个 PR 弄坏了什么"被破坏。
2. **网络抖动 = CI 抖动**：脚本要连 GitHub API / npm registry / endoflife.date
   三家，匿名限流 60 次/小时，任何一家抽风全仓 PR 陪葬。
3. **与已定选线策略打架**：dependency-upgrade spec 明确"不追 current 线、
   Python 等新 minor 且所需库全部支持才切"。若"过时即红"，Python 3.15 发布
   当天所有 PR 全红，逼人在库支持未验证时升级——违反「运行时大版本升级流程」。
4. **"永远最新"不是本仓目标**：目标是"最新稳定线 + 可复现"；追新带来的配置
   churn 正是选线原则要防的。

**折中方案（agent 建议，待人工确认）**：定时任务而非 PR 门禁——每周 cron 跑
`check:outdated`，发现 LAG 自动开 issue（或自动开 lockfile 刷新 PR）。lockfile
minor/patch 属「升级分级」中的例行刷新，机器人可代办；大版本升级涉及库支持
矩阵 + 四端对拍，MUST 走 OpenSpec change，机器人替代不了人。

**安全阀（门禁化 change 的备查要求）**：任何自动化提议升级（机器人开 issue /
刷新 PR）MUST NOT 推荐 `scripts/versions/restrictions.json` 已登记的版本——
由 `check_outdated.py` 统一消费（契约见 dependency-upgrade spec），门禁化
实现时直接复用其过滤结果，禁止另造第二套判断。

**落地形态**：改动触及契约——「过期体检命令」的 MUST NOT 进 CI 条款（改为
"定时可进、PR 门禁不进"）、新增 workflow——属结构性升级，MUST 单独开
OpenSpec change（暂名 `add-freshness-schedule-gate`），待拍板后 propose。
