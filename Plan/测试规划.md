# NetWave 测试规划

> 本文档定义 netwave 的完整测试策略。核心思想：**scikit-rf 是数值 oracle，但 CI 不跑 Python**——
> 用离线生成的 golden 文件把 Python 从测试关键路径上摘出去；跨绑定用同一 core 互相对拍。
> 数据布局与精度分层契约见[总体计划·数据布局](总体计划.md#数据布局) /
> [宪法铁律三](constitution.md#铁律三容差集中在-manifest精度分层是契约)，
> testdata 目录见[总体计划·testdata 跨语言共享测试数据](总体计划.md#testdata--跨语言共享测试数据)。

## 旧库方案的继承与改造

旧库 `RF-Touchstone/test/python/` 的做法：测试运行时起子进程调 Python + scikit-rf，
现场算期望值再和 TS 结果比对。

|           | 旧方案（运行时调 Python）    | netwave 方案（离线 golden）      |
| --------- | ---------------------------- | -------------------------------- |
| CI 依赖   | 每个测试都要 Python + skrf   | CI 零 Python，只读二进制 golden  |
| 速度      | 慢（进程启动 + skrf import） | 快（读文件即比）                 |
| 稳定性    | Python 环境漂移就红          | golden 进 git，结果确定          |
| 三端复用  | 每端各调一次 Python          | 一份 golden，四端共读            |
| skrf 升级 | 悄悄改变期望值               | 每周 job 重生成 + diff，显式发现 |

**保留的内核**：skrf 作为权威 oracle 的地位不变。
**改造的部分**：从"运行时对比"改为"离线生成 golden、运行时只读数据"。

## 测试分层总览

四层按**执行顺序**排列（从内到外、从便宜到贵），CI 依此顺序执行、先失败先短路。
分层不设编号（旧 L1–L4 命名已废除），正式名称即下表第一列——CI job 名、测试目录名、
PR 标签一律直接用这些名字：

| 顺序 | 层名                            | 内容                              | 依赖                                                  | 运行位置        | 容差来源                                                   |
| ---- | ------------------------------- | --------------------------------- | ----------------------------------------------------- | --------------- | ---------------------------------------------------------- |
| 1    | **unit**（单元测试）            | 闭式解自校验 + 边界情况，固定样本 | 无                                                    | `cargo test`    | [manifest](#manifestjson-契约) `core_tol` / bit 级         |
| 2    | **property**（属性测试）        | proptest 随机不变量               | 无                                                    | `cargo test`    | [manifest](#manifestjson-契约) `core_tol` / bit 级         |
| 3    | **golden**（金标准测试）        | 与 skrf 预生成结果比对            | [testdata/](总体计划.md#testdata--跨语言共享测试数据) | 四端各自 runner | [manifest](#manifestjson-契约) 各 case `tol_abs`/`tol_rel` |
| 4    | **cross-binding**（跨绑定对拍） | core/python/node/wasm 互比        | 无                                                    | CI              | 原生三端 bit 级；wasm `tol_rel`                            |

unit + property 在 Rust core 内，覆盖大部分正确性，**完全不碰外部**。golden 锚定"与 skrf 数值一致"。
cross-binding 抓绑定层胶水 bug（字节序、形状转置、零拷贝视图错位）——这是 monorepo 独有的红利。

## unit —— 单元测试（解析自校验）

教科书有闭式解的电路直接手算比对，不需要任何外部库。放 `core/src/**/tests.rs` 或 `core/tests/`。
容差一律从 manifest `core_tol` 读取（[铁律三](constitution.md#铁律三容差集中在-manifest精度分层是契约)），测试代码禁止出现字面量容差。

### 变换恒等类

- `S → Z → S`、`S → Y → S`、`S → T → S` 往返恒等，误差 < [manifest](#manifestjson-契约) `core_tol.roundtrip`
- `se2gmm → gmm2se` 往返恒等（mixed-mode）
- renormalize 到原 z0 应恒等
- `renumber` 后再按逆置换 renumber 应恒等

### 已知解析解类

- **λ/4 阻抗变换器**：给定 Z_line，输入反射/传输有闭式解，直接断言
- **理想 Thru**：`S = [[0,1],[1,0]]`，级联任意网络应还原该网络
- **理想匹配负载**：`S11 = 0`
- **理想功分器 / Wilkinson**：旧库 `designer_wilkinson_splitter.s3p` 作输入
- **无损线时延**：`S21 = exp(-jβl)`，端口延时应精确抵消

### 物理不变量

- 互易网络 `S = Sᵀ`（对称性）
- 无源网络 S 矩阵最大奇异值 ≤ 1（passivity）
- 无损网络 S 酉：`SᴴS = I`
- 因果性：时域冲激响应 t<0 部分能量 ≈ 0

### Touchstone 解析边界

- 1.0 / 1.1 语法、RI / MA / DB 三格式
- 频率单位前缀 Hz/kHz/MHz/GHz
- 注释行 `!`、选项行 `#`、`R`（参考阻抗）选项——`R` 可为标量、每端口列表、复数（`R 50` / `R 50 50` / `R 1e9+1e9j`）
- 噪声数据行（`[Number of Noise Frequencies]`）
- 缺列 / 多余空白 / CRLF / 无尾换行 / 科学计数法 / 负零
- 1 端口到 32 端口（旧库 `ntwk.s32p`）
- 写出→读回 **bit 级一致**（写出契约 = shortest-roundtrip 格式化，
  见[精度标准](#精度标准)；断言用 `==` 不是容差）

## property —— 属性测试（proptest）

Rust 版快速检查（quickcheck 的现代替代，事实标准）。随机生成**合法** Network，断言不变量。
旧库 `randomTouchstoneMatrix.ts` 是同一思路的雏形。
容差同样从 [manifest](#manifestjson-契约) `core_tol` 读取：测试 helper 启动时读一次 manifest，注入常量 `TOL`。

```rust
// 伪代码示意；TOL = testdata/manifest.json 的 core_tol
proptest! {
    #[test]
    fn s2z_roundtrip(s in arbitrary_network(1..=8)) {
        let back = z2s(s2z(&s));
        prop_assert!(close(&s, &back, TOL.roundtrip));
    }
    #[test]
    fn cascade_identity(n in arbitrary_network(2..=4)) {
        let thru = ideal_thru(n.nfreq);
        let c = cascade(&n, &thru);
        prop_assert!(close(&n, &c, TOL.cascade));
    }
    #[test]
    fn touchstone_roundtrip(nw in arbitrary_network(1..=8)) {
        let txt = write_touchstone(&nw);   // shortest-roundtrip 格式化
        let back = parse_touchstone(&txt);
        prop_assert_eq!(nw.s_bits(), back.s_bits());   // bit 级，非容差
    }
}
```

关键属性清单：

- 参数往返恒等（S↔Z/Y/T/H/G）
- 级联维度正确、级联恒等（∘ Thru）
- renumber 是置换（保多重集）
- Touchstone 写出→读回恒等
- passivity 在级联下保持（无源级联仍无源）
- FFT 时域→频域往返恒等

## golden —— 金标准测试（skrf oracle）

### golden 生成（`testdata/gen_golden.py`）

唯一运行 Python 的地方，**离线、按需、不进主 CI**。用 skrf 计算期望值，写成交错复数 f64 裸二进制。
环境用 uv 管理（`pyproject.toml` + `uv.lock` 钉死 skrf/numpy 版本，跑法 `uv run python gen_golden.py`，见[总体计划·Python 环境管理](总体计划.md#python-环境管理uv)）。

```python
# 伪代码示意
import skrf, json, numpy as np, pathlib
def gen(name, net, op):
    out = APPLY[op](net)                       # 如 net.z / net ** net2 / net.se2gmm
    out.s.astype('<c16').tofile(f'golden/{name}.bin')   # 交错 re,im，小端
    manifest.append({"case": name, "input": ..., "op": op,
                     "golden": f"{name}.bin", "shape": list(out.s.shape),
                     "tol": 1e-12})
```

- 输入样本：skrf 自带测试集 + 旧库 `RF-Touchstone/test/samples/`（BSD 许可，保留版权头）
- 覆盖操作：parse、S↔Z/Y/T/ABCD、cascade、deembed、renumber、mixed-mode、TDR/step response
- 每个操作用多个不同端口数/格式的样本，边界情况（复数 z0、非 50Ω）单独造

### manifest.json 契约

三端 runner 的唯一输入清单，**精度标准集中在此**，避免三端各写各的容差。

```json
{
  "version": 2,
  "layout": "interleaved-f64-le",
  "core_tol": { "roundtrip": 1e-12, "cascade": 1e-11, "fft_time": 1e-9 },
  "cases": [
    {
      "id": "s2z_ntwk1",
      "input": "touchstone/ntwk1.s2p",
      "input_kind": "committed",
      "op": "s2z",
      "golden": "golden/s2z_ntwk1.bin",
      "output_kind": "complex",
      "shape": [101, 2, 2],
      "tol_abs": 1e-12,
      "tol_rel": 1e-10
    }
  ]
}
```

schema 要点：

- `core_tol`：收纳 unit / property 层（Rust core 内自校验，不碰外部数据）的默认容差
  （[铁律三](constitution.md#铁律三容差集中在-manifest精度分层是契约)：容差只在 manifest，这两层不例外）；
- `output_kind`：`complex`（交错 f64）/ `float`（如 TDR 时间轴）/ `int`（如 renumber 置换），
  golden 二进制按此解释；
- `input_kind`：`committed`（进 git）/ `generated`（CI 内由脚本生成，如 50MB 大文件样本，
  见[性能基准](#性能基准criterion)）；
- `tol_abs`/`tol_rel`：wasm 类用例只声明 `tol_rel`（绝对容差在大值上误报，
  见[铁律三](constitution.md#铁律三容差集中在-manifest精度分层是契约)）。

### 三端 runner（薄，只读数据 + 断言）

各端就近放，逻辑一致：读 manifest → 加载 input → 跑对应 API → 读 golden → 按 tol 比对。

| 端     | 位置                          | 读 golden 方式                |
| ------ | ----------------------------- | ----------------------------- |
| Rust   | `core/tests/golden.rs`        | `std::fs::read` → `&[f64]`    |
| Python | `python/tests/test_golden.py` | `np.fromfile(dtype='<c16')`   |
| Node   | `node/tests/golden.test.ts`   | `new Float64Array(buf)`       |
| WASM   | `wasm/tests/golden.test.ts`   | 同 Node（浏览器/worker 环境） |

比对统一用 `max(abs_diff, rel_diff*scale) < tol`，容差从 manifest 取。

### skrf 升级守护

- 独立 workflow `golden-refresh.yml`，**每周**跑 `gen_golden.py` 重新生成，`git diff` golden 文件；
- 有 diff → 开 issue/PR 报告"哪些用例数值变了、变了多少"，人工确认是 skrf 修 bug 还是我们回归；
- 主 CI 永不跑 Python，保持快与稳。

## cross-binding —— 跨绑定一致性对拍

monorepo 独有：四端都委托同一份 Rust 算法。断言强度按
[铁律三](constitution.md#铁律三容差集中在-manifest精度分层是契约)的精度分层契约执行：
**同机同架构的原生三端 bit 级互比；wasm 跨编译目标，用相对容差。**

```text
同一 manifest 用例
   ├─ core (Rust)      ┐  同一编译产物、同一指令序列
   ├─ python (PyO3)    ├─ → 两两 bit 级一致（== 断言）
   └─ node  (napi)     ┘
   └─ wasm (bindgen)      → 对原生结果用相对容差（simd128/无 SIMD 路径 ulp 差异必然存在）
```

- 触发：CI 里一个 `cross-binding` job，构建四端后跑同一组用例；
- 断言：原生三端 bit 级——绑定层的字节序、stride 转置、视图错位是天文数字级偏差，
  bit 级正是抓这种胶水 bug 的；wasm 用 manifest 的 `tol_rel`（典型 1e-14），
  预期多数用例仍 bit 级命中，SIMD 分发路径用例容差通过即正常；
- 价值：golden 保证"跟 skrf 对"，cross-binding 保证"四端互相也对得上"——两者互补，缺一不可。

## 精度标准

| 类别                       | 标准       | 说明                                                                             |
| -------------------------- | ---------- | -------------------------------------------------------------------------------- |
| 解析变换往返（S↔Z/Y/T）    | 绝对 1e-12 | 纯矩阵运算，f64 极限内                                                           |
| Touchstone round-trip      | **bit 级** | 写出契约 = shortest-roundtrip 格式化（ryu 类：读回原值的最短十进制，无损可证明） |
| 级联 / deembed             | 绝对 1e-11 | 多次矩阵乘累积                                                                   |
| mixed-mode                 | 绝对 1e-12 | 线性变换                                                                         |
| FFT 时域（TDR/step）       | 绝对 1e-9  | DC 外推 + 数值 FFT 误差                                                          |
| cross-binding 原生三端对拍 | **bit 级** | 同机同架构同一编译产物，仅允许 `==`                                              |
| cross-binding wasm 对拍    | 相对 1e-14 | 跨编译目标，SIMD 路径 ulp 差异必然存在                                           |

- 写出 Touchstone 用 shortest-roundtrip 格式化（如 `ryu`/`formatting` 类算法），
  不规定固定位数——旧"≥15 位有效数字"作废（15 位定长做不到 bit 级往返）；
- 所有容差以 [manifest.json](#manifestjson-契约)（含 `core_tol`）为准，本表是其默认值来源。

## 性能基准（criterion）

Rust 侧用 `criterion` 建基准，防性能回归（旧库"大文件卡死"是立项动因，必须守住）。

| 基准                    | 目标                     |
| ----------------------- | ------------------------ |
| 解析 50MB s4p           | < 100ms（memmap2+rayon） |
| S→Z（1001 点 × 4 端口） | < 5ms                    |
| 级联 1000 次            | < 50ms                   |
| FFT 时域 1M 点          | < 200ms                  |

- CI 里跑 criterion 并与上次 main 对比，显著劣化（>20%）则失败；
- 大文件样本用生成脚本造（不提交超大文件到 git，用 LFS 或 CI 内生成）。

### 基线跨提交持久化（阶段 2 任务）

GitHub Actions 每次 runner 都是干净的，`target/criterion/` 不跨 run 保留——
当前 `ci.yml` 的 bench job 只能测同机噪声，**做不到与历史提交对比**。
阶段 2 真实基准落地时改造为"基线提交进仓库"：

- CI 跑 `cargo bench -- --baseline=<仓库基线名>`，把 `change/estimates.json`
  导出到仓库内 `benches/baseline/` 提交（commit message 标注来源与 runner）；
- 基线命名空间隔离环境：CI 只用 `ci`，本地只用 `local`（`target/` 被
  gitignore，天然不入库）；门禁脚本只读仓库里那份 CI 基线，
  本地机器噪声不混进判定；
- 性能变化随 PR diff 可见，可审计可 review——与
  [manifest.json 契约](#manifestjson-契约)同一套治理思路。

## 覆盖率与工具

**覆盖率底线：全端 100%（行覆盖），unit 层零豁免**——core / python / node / wasm 四端
所有产码行必须被测试执行到，CI 低于 100% 即失败。唯一允许的例外是**结构性不可达代码**
（`unreachable!()`、平台专属分支、防御性 error 转换），必须逐条显式标注豁免并在
manifest 旁登记理由，禁止整文件/整目录批量豁免：

- Rust：`#[coverage(off)]` + 注释理由；
- Python：`# pragma: no cover` + 注释理由；
- TS/JS：`/* istanbul ignore next */` + 注释理由。

| 工具                       | 用途                               | 门槛                                                        |
| -------------------------- | ---------------------------------- | ----------------------------------------------------------- |
| `cargo llvm-cov`           | Rust 覆盖率（core + 三绑定 crate） | lines/regions/functions 100%                                |
| `pytest-cov`               | Python 绑定层                      | lines 100%（`--cov-fail-under=100`）                        |
| `vitest --coverage`        | Node / WASM / viewer               | lines/branches 100%（`branches: 100` 阈值写进 vitest 配置） |
| `cargo clippy -D warnings` | lint 即错误                        | —                                                           |
| `cargo fmt --check`        | 格式                               | —                                                           |

100% 行覆盖是**下限不是目标**：执行到 ≠ 断言对。数值正确性仍由
golden / property / cross-binding 三层负责（见[测试分层总览](#测试分层总览)），
覆盖率只兜底"有没有代码没被任何测试碰过"。

## CI 集成

| workflow             | 触发        | 内容                                                                                                                                |
| -------------------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`             | PR / push   | unit+property（cargo test）、golden 三端、cross-binding 对拍、clippy、fmt、覆盖率、criterion（按[测试分层总览](#测试分层总览)顺序） |
| `golden-refresh.yml` | 每周 / 手动 | 跑 gen_golden.py，diff golden，异常开 issue                                                                                         |

## 阶段映射

阶段模型（[总体计划·分阶段路线图](总体计划.md#分阶段路线图)）：**地基从阶段 0 就是四端的**，功能变更 DoD = core + 三绑定 + 四端测试全绿。

| 阶段            | 测试交付                                                                                        |
| --------------- | ----------------------------------------------------------------------------------------------- |
| 0 脚手架        | CI 骨架、clippy/fmt、criterion 空基准、cross-binding 三绑定 hello world 对拍                    |
| 1 测试基础设施  | manifest 契约测试、gen_golden.py 产物自检（假 golden 必须失败）、四端 golden harness 冒烟       |
| 2 Touchstone    | unit 解析边界、property round-trip、parse golden **四端全绿**、cross-binding 常态跑、大文件基准 |
| 3 wasm 性能定标 | wasm 基准进 CI job、阈值回归即失败；提速候选项每项带前后基准对比                                |
| 4 Network       | unit 变换恒等/解析解、property 往返属性、变换+级联+TDR golden 四端、cross-binding               |
| 5 Circuit       | unit 已知电路、求解 golden 四端、cross-binding                                                  |
| 6 绑定高级能力  | GIL/AsyncTask 并发正确性测试、wasm 视图失效强制机制测试、CSV 往返、覆盖率达标                   |
| 7+ 高级功能     | 每个新模块补 unit + property + golden（四端），golden 增量生成                                  |
