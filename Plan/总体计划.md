# NetWave 总体计划

> 一个频域散射矩阵（S-matrix）电路求解引擎，Rust 高性能核心 + Python/TypeScript 双端零拷贝绑定，
> 同一套程序同时服务 RF 与光学（光子学）。

## 项目定位

### 要解决的问题

- 现有纯 TypeScript 实现（`RF-Touchstone`）用 `mathjs` 的 `Complex[][][]` 对象数组做计算，
  缓存不友好、堆分配严重，**大 Touchstone 文件（>50MB）直接卡死**。
- 只覆盖 Touchstone 解析，缺少 Network / Circuit 等完整体系。
- 缺少 Python 端能力，无法与 scikit-rf 生态互通。

### 核心定位

本质是 **频域散射矩阵线性网络求解器**：

- RF 的 S 参数与光子学的 S 参数在数学上是同一对象（端口上的复数相量 + 散射矩阵）。
- 因此引擎**域无关**：同一套核心可同时给 RF 和光学使用（对标 Lumerical INTERCONNECT 把 RF 算法适配到光学）。
- 只做频域、基于 S-parameter，不做时域仿真（区别于 circulax 等的时域方向）。

### 命名

- 仓库/品牌名：**`netwave`**（network + wave，域无关，短、稳妥、撞名风险低）。
- 核心类型命名**不出现 `rf` 前缀**，使用 `Port` / `Network` / `Circuit` / `Wave` 等中性词；
  参考阻抗 `z0` 作为端口属性，而非全局常量——这是让 RF 算法透明复用到光学的关键。
- tagline：*A frequency-domain scattering-matrix circuit solver for RF and photonics.*

## 语言与架构选型

### 核心语言：Rust

决定性因素是 **双端（Python + TypeScript）+ 浏览器** 的零拷贝需求：
Rust 是唯一在三个目标上都有一线零拷贝绑定工具链的语言。

| 端 | 方案 | 零拷贝机制 |
|---|---|---|
| Python | PyO3 + `numpy` crate + maturin | `PyArray::from_borrowed_data`：ndarray 直接以 Rust 堆内存为后端，cleanup 回调在 Python 侧释放时回收（`PyArrayView` 仅用于输入方向借用） |
| Node | napi-rs | `ArrayBuffer` + `External` 后端内存，JS 端拿 `Float64Array` 视图 |
| 浏览器 | wasm-bindgen | 数据留在 WASM 线性内存，JS 拿 `new Float64Array(memory.buffer, offset, len)` 视图 |

对比 C++（Eigen 强但绑定工程成本高）/ C（ctypes 有拷贝开销），Rust 在绑定层与交叉编译发版上优势明显。

### 数据布局

统一用 `(nfreq, nports, nports)` **交错复数扁平 f64**（complex128）：`[re, im, re, im, ...]`。

- 与 scikit-rf `Network.s`（同为 `(freq, ports, ports)` complex128 ndarray）**逐字节相同**，
  零拷贝即同一块内存的 reinterpret，无需转换、无 strided 拷贝；
- 选 `(freq, p, q)` 而非 `(p, q, freq)` 的理由（详见[宪法铁律一](constitution.md#铁律一数据布局是契约不是实现细节)）：Touchstone 按频率逐行 →
  流式解析线性拷贝无转置；热路径逐频点做 (p×p) 矩阵运算，每频点矩阵连续；沿大轴 freq 切 rayon 负载均衡；
- 代价：单条 trace（固定 p,q 扫频）跨步——属显示/IO 路径，非热路径，按需跨步视图/转置。

### 大文件

Rust 侧用 `memmap2` + `rayon` 并行流式解析，根治大文件卡死；50MB s4p 预期几十毫秒级。

并行模型：rayon 是**原生 OS 线程池**（默认 = 逻辑核数）+ work-stealing 任务调度，
同步阻塞式并行，非协程非进程——适合纯 CPU 密集的复数矩阵运算，数据不跨进程搬运。

浏览器端约束：wasm32 默认**单线程**，rayon `par_iter` 自动退化为串行，代码无需改动。
多线程需 wthreads（Web Worker + SharedArrayBuffer 共享线性内存），
前提是页面具备跨域隔离（COOP/COEP 响应头）。注意：**这是部署方式问题，不是浏览器兼容问题**——
主流浏览器（Chrome/Edge/Firefox 87+/Safari 15.2+）均支持该 API，
但 GitHub Pages（不支持自定义响应头）、被第三方页面 iframe 嵌入、非 HTTPS 等场景拿不到跨域隔离，
SharedArrayBuffer 即被禁用。故多线程作为**可选增强**：
运行时检测 `crossOriginIsolated`/`SharedArrayBuffer` 可用才启用，否则单线程回退；
零拷贝视图不受此影响，任何场景功能正确性不变，仅大文件解析变慢。
性能底线（[宪法铁律六](constitution.md#铁律六大文件性能是立项理由必须守住)）适用于原生端（Python/Node）；
浏览器端单线程性能由阶段 3 定标（见[分阶段路线图](#分阶段路线图)）。

### 计算库分工与 GPU 否决

NumPy 的职责在 Rust 端拆分承担，TS 端被架构消解：

| 能力 | Python（对照） | Rust 核心 | TS / 浏览器 |
|---|---|---|---|
| N 维数组 + 视图 | `numpy.ndarray` | `ndarray`（容器，视图/strided 语义几乎相同） | 原生 typed array 视图，**无任何数学库** |
| 复数 | `complex128` | `num-complex` | 交错 re/im，无对象 |
| FFT | `scipy.fft` | `rustfft` | 在 wasm 内跑，JS 不需要 |
| 稠密线性代数 | LAPACK/BLAS | `faer`（倾向，见[待办 / 待核实](#待办--待核实)） | 不需要 |

热路径逐频点取每频点 p×p 连续块喂 `faer`（零拷贝借用），沿 nfreq 由 rayon 切分；
`ndarray` 只做容器与切片，不做逐元素计算。

**GPU（WebGPU/WebGL/CUDA）已评估，不采用**，任何端都不引入：

- 精度一票否决：WebGPU（WGSL）核心规范无 f64，WebGL 只有 f32——直接违反[铁律一](constitution.md#铁律一数据布局是契约不是实现细节)（complex128）与
  manifest 容差（1e-12），golden 对拍必红；
- 负载不匹配：netwave 是"数千个独立的 2×2~8×8 复数小矩阵"+文本解析，非大而规则稠密运算，
  GPU 调度与显存搬运开销远超计算收益；CPU 端 rayon+SIMD 才是正确匹配；
- 摧毁零拷贝：上 GPU 意味着每次计算 upload→kernel→download 两次显式拷贝，
  消灭这种拷贝正是立项动机（[要解决的问题](#要解决的问题)）；
- 生态冲突：skrf 算法全是 CPU LAPACK 思路，Rust GPU 生态无成熟复数矩阵批处理求解器，
  违反[功能范围](#功能范围对标-scikit-rf--signalintegrity)"不重新发明算法"原则。
  WebGL 在 viewer 中只允许用于**渲染**（曲线图），不得承担计算。
  将来若重开 GPU，唯一合理场景是原生端百端口大电路/大规模矢量拟合（Python 侧 CuPy），与浏览器无关。

### 跨语言 API 面契约（防"越改越乱"的闸门）

计算全在 core，三端用户被迫使用 core 定义的 API 面——规矩必须提前钉死，
否则功能缺口会从各端私生长数学层撕开。核心认知：**只存一份主数据（S 矩阵），
Z/Y/T/H/G 全部是调用时现算的派生值不落盘**——不存在"改了一边另一边同步"问题，
真正要定义的是结构变更时新数据的来源语义。

**三层契约（三端一致）：**

| 层 | 内容 | 规矩 |
|---|---|---|
| 数据层 | 交错 f64 缓冲的**可写视图**（改元素、切片、置零、拷贝） | 三端直接暴露，随便玩。Python = ndarray 花式索引；TS = typed array 索引/`fill`/`subarray` + 可选一行辅助（`setS`/`zeroTrace`，纯视图糖无数学）。这些不是"数学库"操作，TS 无库不构成障碍 |
| 计算层 | 域动词：`to_z/to_y/…/cascade/se2gmm/tdr/renormalize` | **唯一数值权威，全在 core**。绝不暴露 `matmul/solve/inv/eig` 等线代原语——一旦暴露，用户拿裸 buffer 自拼矩阵乘，数值真相裂成四处（违反铁律三精神）。功能缺口走 OpenSpec 加进 core 再四端同步发版 |
| 结构层 | 改形状/元数据：`set_frequencies/interpolate/renumber/set_z0_reference/add_port` | core 动词，重分配内存；**操作后旧视图一律作废，必须重新获取**。失效强度分端：wasm 叠加 memory.grow detach 是**硬件强制**；原生端（Python cleanup 回调 / Node External）旧视图技术上仍可读，**无法强制作废**——契约为"旧视图行为未定义"，靠类型层面返回新对象（不提供原地修改型结构动词）+ 文档约束。API 文档必须写明此规则，否则用户拿悬空视图静默写坏数据 |

**`z0` 双动词（语义分叉必须拆开，防止一个名字两种物理）：**

- `renormalize(z0)` —— **计算层**：s 数据跟着重算（对应 skrf 的 z0 setter 语义），主数据变更；
- `set_z0_reference(z0)` —— **结构层**：只改端口参考标签，s 不动，派生量（z/y）变。

**频率轴跨端契约（数据契约的另一半）：**

- 频率轴内部**永远存 f64 Hz**；单位（Hz/kHz/MHz/GHz）只是 Touchstone IO 与显示层的元数据，
  不进计算层；
- Python 端 `frequency` 暴露为零拷贝 f64 ndarray（Hz）；TS/wasm 端为 Float64Array 视图；
- skrf 的 `f_scaled`/`unit` 概念只存在于 Python 绑定层的换算糖，core 无此概念。

**数据对齐规则（结构变更的语义，阶段 4 前定案）：**

1. **无隐藏派生状态**：Network 不缓存任何派生结果（先做"不缓存，每次现算"，简单即正确）。
   用户直接写视图后，下一次 `to_z()` 自动基于新数据，无需 sync 调用——这是"裸数组可写"
   语义成立的前提。
2. **频率轴与 S 矩阵原子变更**：改频率永远是 `(freq_axis, s[:, :, :])` 一个事务，禁止
   分开 setter（skrf 的 `ntk.frequency = ...` 单独赋值不重算 s，是陷阱不是便利）。
3. **新增频点的 S 值来源必须显式**：`add_frequency(f, method)` 的 method 是必填参数——
   插值（线性/log-mag+phase，对齐 skrf `interpolate_single_point`）/ 用户指定完整 p×p 矩阵 /
   零填充（默认禁止，仅显式选择）。**不存在"默认加一行"**——物理上凭空频点无真值。
4. **命名三端一致**：同一操作三端同名（`se2gmm` 处处 se2gmm，TS 只做机械 camelCase），
   以 skrf 术语为权威；API 完备性清单 = [功能覆盖规划](功能覆盖规划.md)的 skrf ∩ SI 交集。
5. **Python 端允许 numpy 接管数据层**（接 skrf 生态的意义），但边界：就地改写语义写进文档；
   用户自算结果不受 golden 容差保护，回灌 core 需走构造/解析入口。

## 仓库结构（Monorepo）

核心 crate 与两个绑定**必须同仓同步发版**（ABI 严格同步，避免版本漂移）。

**采用平铺布局**：子项目少且稳定，不引入 `crates/`、`packages/` 分组层——
分组约定只会制造"某个 crate 该进哪个文件夹"的伪决策，平铺让目录语义归一、加子项目零判断。

```text
netwave/
├── core/          # Rust 核心 crate：S/Y/Z/H/G 参数、Network、Circuit 求解
│   ├── touchstone 解析（memmap2 流式）
│   ├── 复数多维数组（ndarray + num-complex + rustfft）
│   └── 矩阵运算（faer 倾向，选型见下方说明）
├── python/        # Rust crate + PyO3 + maturin → PyPI（NumPy 零拷贝）
├── typescript/  # 单一 npm 包 netwave：exports 条件自动分发 node/browser
│   ├── native/      # Rust crate + napi-rs → .node（ArrayBuffer 零拷贝）
│   ├── wasm/        # Rust crate + wasm-bindgen + wasm-pack → 浏览器内存视图
│   ├── src/         # 入口壳：index.node.mjs / index.browser.mjs /
│   │                #   standalone.js（纯 HTML 零构建）/ netwave.worker.js
│   │                #   （预置 Worker 胶水，防主界面卡死，零数值逻辑）
│   ├── dist/        # 全部构建产物（exports 只指向这里，发布白名单）
│   └── test/        # vitest workspace：native + wasm 两项目
├── viewer/        # 纯 TS Web Components（框架候选 Lit，WebUI 立项时定案）→ npm
├── testdata/      # 跨语言共享测试数据：samples、skrf golden、manifest、gen_golden.py
├── Cargo.toml     # [workspace] members = ["core","python","typescript/native","typescript/wasm"]
├── pnpm-workspace.yaml  # pnpm workspace 包：typescript / viewer（包管理器 pnpm，见下方说明）
├── Plan/          # 本目录
└── .github/workflows/   # 三平台矩阵构建（cargo-zigbuild / napi-rs CLI / maturin）
```

说明：`core` 的稠密线代后端倾向 `faer`，最终选型在[待办 / 待核实](#待办--待核实)跟踪，
阶段 4 前用 criterion 实测定案；viewer 框架候选 Lit，WebUI 立项时定案。

### 目录名与发布名解耦

**目录一律用短名**（去掉仓库名已提供的前缀，避免 `netwave/netwave-core` 式冗余），
**发布名在各清单文件独立声明**——两者完全解耦，三个注册表都只认清单字段、看不到目录名：

| 目录 | 清单字段 | 发布名 | 安装方式 |
|---|---|---|---|
| `core/` | `Cargo.toml` `[package] name` | crates.io: `netwave`（可选，纯自用可 `publish=false`） | `cargo add` |
| `python/` | `pyproject.toml` `[project] name` | PyPI: `netwave` | `uv add netwave`（或 `uv pip install netwave`） |
| `typescript/` | `package.json` `name` | npm: `netwave`（单包，exports 条件自动分发 node/wasm + 纯 HTML standalone + 预置 worker） | `pnpm add netwave` |
| `viewer/` | `package.json` `name` | npm: `@netwave/viewer` | `pnpm add @netwave/viewer` |

命名原则（2026-09-21 定案）：**能统一处统一为 `netwave`，同一注册表内必须
区分处加后缀**。三注册表主名一律 `netwave`。npm 侧 TypeScript 走**单包单目录**
（`typescript/` 一个目录、一个 `netwave` 包）：`exports` 条件在 import 时自动
选 napi（node 条件）或 wasm（browser/default 条件）产物，打包器只拉命中分支，
消费者产物体积无感；install 磁盘占用由 napi 按平台 `optionalDependencies`
（`os`/`cpu` 标签）控制。**不再拆 `@netwave/node`/`@netwave/wasm`/伞形包三包**
——三包方案对体积无优势（伞形包 dependencies 同样两个都装），只多一套同版本
同步机器。纯 HTML 用户走 `./standalone` 子路径或 CDN，零 Node.js；**不发 UMD**
（`<script type="module">` 即标准答案）。未来网页端插件用 `@netwave/<功能名>`
（预留 `@netwave/converter`——Touchstone 格式转换 web component、
`@netwave/touchstone`——Touchstone 显示等网页插件）。

纪律：目录一律短名，绝不混用 `core` 与 `netwave-core` 两种风格——一致性本身消灭决策。
`python/`、`typescript/native/`、`typescript/wasm/` 里的 Rust crate 名
（`netwave-python`/`netwave-native`/`netwave-wasm`）设 `publish = false`，
它们只经 maturin/napi/wasm-pack 发到 PyPI/npm，无人从 crates.io 安装。

包名方案：

- crates.io: `netwave`（可选）
- npm: `netwave`（单包，exports 条件分发 node/wasm + standalone + worker）、
  `@netwave/viewer`（预留 `@netwave/converter`、`@netwave/touchstone`）
- PyPI: `netwave`
- GitHub: `netwave`

### testdata/ —— 跨语言共享测试数据

**测试数据集中、测试代码就近**：跨语言能共享的是"数据 + 期望值"，断言逻辑各语言用原生框架写。
`testdata/` 是唯一被 Rust / Python / Node / WASM 四端测试共同读取的目录，CI 里**不跑 Python**。

```text
testdata/
├── touchstone/          # 输入样本：复用 skrf 测试集 + 旧库 RF-Touchstone/samples
├── golden/              # skrf 预生成的期望输出（交错复数 f64 裸二进制，布局见下方说明）
│   ├── s2z_*.bin
│   ├── cascade_*.bin
│   └── ...
├── manifest.json        # 每个用例：输入文件、操作、期望 golden 文件、容差（tolerance）
└── gen_golden.py        # 唯一碰 Python 的脚本：离线跑 skrf 生成 golden（本地/按需/每周 CI）
```

- **生成一次，提交进 git**；三端 runner 只读 `testdata/`，零 Python 依赖；
- `manifest.json` 给每个用例声明容差（解析变换 1e-12、FFT 时域 1e-9），三端读同一容差，精度标准不漂移；
- golden 用交错复数 f64 裸二进制，顺带验证[数据布局](#数据布局)的序列化约定；
- 每周独立 CI job 重跑 `gen_golden.py` 并 diff，捕捉 skrf 升级导致的数值漂移。

完整测试分层（unit / property / golden / cross-binding）见[测试规划·测试分层总览](测试规划.md#测试分层总览)。

### Python 环境管理：uv

**Python 侧一律用 [uv](https://docs.astral.sh/uv/) 管理环境，禁止裸 `pip` + 系统 Python。**

- 一切 Python 项目（含 `testdata/gen_golden.py` 的 skrf 环境、`python/` 绑定开发环境）
  必须有 `pyproject.toml` 声明依赖，`uv.lock` 锁版本进 git——golden 数值可复现依赖依赖版本确定；
- 常用命令：`uv init`（建项目）、`uv add <pkg>`（加依赖）、`uv run <cmd>`（在项目环境内跑，
  自动建/同步 `.venv`）、`uv sync`（按 lock 重建环境）；`uv pip` 子命令仅作过渡兼容，
  主干工作流不直接用；
- `gen_golden.py` 跑法：`uv run python gen_golden.py`，skrf/numpy 版本由 lock 钉死，
  与[铁律四](constitution.md#铁律四skrf-是-oracle但主-ci-不跑-python)"golden 进 git 结果确定"一致；
- maturin 作为 dev dependency 进 `pyproject.toml`（`uv add --dev maturin`），构建命令
  `uv run maturin develop`，不再全局装 maturin；
- uv 也可管理 Python 解释器本身（`uv python pin 3.14` 钉开发版，`.python-version`
  进 git），CI 与本地版本一致，不依赖系统 Python。

### Node.js 包管理：pnpm

**Node 侧一律用 [pnpm](https://pnpm.io/)，禁用 npm / yarn。**

- 理由：monorepo（typescript/viewer 两包）是 pnpm workspace 主场；内容寻址存储 + 硬链接，
  安装速度与磁盘占用全面优于 npm；严格 `node_modules` 布局杜绝幽灵依赖；
  yarn v2+ 的 PnP 方案生态已弃（Meta 自己转 pnpm），无选型悬念；
- 版本钉死：根 `package.json` 写 `"packageManager": "pnpm@<版本>"`，配合 corepack 启用，
  CI 与本地自动同版本；包声明文件为 `pnpm-lock.yaml`（进 git，唯一真相）；
- workspace：根 `pnpm-workspace.yaml` 列出 `typescript` / `viewer`；跨包依赖用
  `workspace:*` 协议，发版前 `pnpm -r` 递归执行构建/测试；
- 常用命令：`pnpm install` / `pnpm -C node add <pkg>` / `pnpm -r build` / `pnpm dlx <cli>`；
  `@napi-rs/cli` 等工具装为项目 devDependency，不装全局（避免 nvm 切 Node 版本后 CLI"消失"）。

## 功能范围（对标 scikit-rf / SignalIntegrity）

主体 = **`Touchstone` / `Network` / `Circuit` / `Frequency` 四大主类**及其函数，
外加 `constants` 模块（单位前缀、物理常数、参数类型/格式枚举）。
功能范围三层：**骨架 = skrf ∩ SI 交集**；**旧库 rf-touchstone 功能 100% 覆盖是硬约束**
（H/G 参数、噪声行解析等来自旧库而非交集）；**单库独有功能**（passivity 等）逐条显式批准。
其余各自独有功能延后（详见[功能覆盖规划](功能覆盖规划.md)）。

- **Touchstone IO**：1.0 / 1.1 解析与写出，RI/MA/DB 格式，流式大文件。
- **Network**：S/Y/Z/H/G/T 参数互转，级联（`**` / deembed），renumber，mixed-mode（se2gmm/gmm2se），
  passivity 检查，时域变换（TDR / impulse response，FFT）。
- **Circuit**：多网络互连求解（`S = ([X^T]* - [C])^-1` 一类方法），auto_reduce 优化。
- **Calibration / Deembedding**（后续阶段）：EightTerm、TRL、IEEEP370 等。
- **Vector Fitting**（后续阶段）：有理拟合 + SPICE 等效电路导出。

算法**不重新发明**：照搬 scikit-rf 已验证的教科书算法，测试直接采用 scikit-rf 的测试数据做 golden test，
保证正确性且工作量可控。

## 旧仓库处理

- `RF-Touchstone`（`rf-touchstone` npm 包）：**不做兼容层**。旧库的计算 API 基于 `mathjs`
  的 `Complex[][][]` 对象数组，与 netwave 的交错复数扁平 buffer 无法兼容，强行兼容会丢掉
  零拷贝优势。README 指向 netwave + 迁移对照表后归档。
- 当前版本仅 `0.0.7`，让用户迁移的成本低于维护兼容层的成本。

## 分阶段路线图

**阶段模型铁则：地基从阶段 0 就是四端的。** 从阶段 2 起，每个功能变更的完成定义（DoD）=
 core 实现 + 三绑定（python/node/wasm）同步暴露 + 四端测试全绿。功能可以小（阶段 2 只有
 Touchstone 读写），但每一阶段四端都立起来，cross-binding 对拍从阶段 2 就常态跑。

- **阶段 0 — 脚手架**：monorepo 结构、CI 三平台矩阵、`netwave`（core）空 crate + napi/PyO3/wasm 三绑定 hello world，
  验证零拷贝 buffer 往返。
- **阶段 1 — 测试基础设施**：`testdata/` 布局落地（skrf 测试集 + 旧库样本，保留版权头）、
  `manifest.json` 契约实现（`core_tol` + per-case `tol_abs`/`tol_rel`）、`gen_golden.py` 最小可用版
  （首批 parse 用例）+ golden 裸二进制进 git、`golden-refresh.yml` 周 CI、四端 golden 读取 harness。
  DoD = 至少一个 parse 用例走通 manifest → golden → 四端断言全链路（含"假 golden 必须失败"自检）。
- **阶段 2 — Touchstone 核心**：Rust 流式解析（memmap2+rayon）、交错复数数据模型、RI/MA/DB、1.0/1.1；
  用 scikit-rf 测试集做 golden test；三绑定同步暴露 parse/write API，四端 golden 全绿。
- **阶段 3 — wasm 性能定标与提速**：wasm 单线程基准 harness（同一语料对比原生端）；实测 50MB s4p
  解析/写出往返耗时，把[铁律六](constitution.md#铁律六大文件性能是立项理由必须守住)的 wasm"单独定标"
  落成具体阈值并回写宪法；提速研究候选：`simd128`、流式解析分块大小调优、线性内存 growth 与
   allocator 选型，可选验证 wthreads 多线程增强。DoD = 基线数值进 CI benchmark job（显著劣化即失败），
  阈值写回铁律六。
- **阶段 4 — Network**：参数互转、级联、renumber、mixed-mode、passivity、FFT 时域（四端同步）。
- **阶段 5 — Circuit**：互连求解、auto_reduce（四端同步）。
- **阶段 6 — 绑定高级能力**：Python GIL 精细化（`allow_threads` 全量清单）、Node AsyncTask 异步面、
  wasm 视图失效强制机制、CSV 导入导出；旧 `rf-touchstone` 迁移文档（无兼容层）。
  注意：零拷贝绑定本身从阶段 0 起就有，本阶段不是"做绑定"，是绑定层的深水区收尾。
- **阶段 7+ — 高级功能（延后，按需逐项加）**：Calibration / Deembedding / Vector Fitting 等。
- **阶段 8 — 光学适配验证**：用域无关 API 跑通一个光子学 mzi/ring 示例，验证 RF/光学同源。
- **viewer（不在本路线图，独立立项）**：最小版 = Smith 圆图 + trace 图，只读 typed array 视图做渲染
  （见[计算库分工与 GPU 否决](#计算库分工与-gpu-否决)：WebGL 仅渲染不计算）；框架候选 Lit，立项时定案。
