# NetWave 测试规划

> 核心思想：**scikit-rf 是数值 oracle，golden 由 CI 在 oracle 的 uv 环境现算、
> 不入库**——skrf 圈禁于 oracle 环境，各端测试关键路径零 Python；跨绑定用
> 同一 core 互相对拍，阅卷集中在 `oracle/scripts/compare_cross.py`。
> 精度分层契约见[铁律三](../openspec/specs/project-governance/spec.md)，
> oracle 目录布局见 [oracle/README.md](../oracle/README.md)。

## 测试分层总览

四层按**执行顺序**排列（从内到外、从便宜到贵），CI 依此顺序执行、先失败先短路。
分层不设编号，正式名称即下表第一列——CI job 名、测试目录名、PR 标签直接用：

| 顺序 | 层名                            | 内容                              | 依赖                   | 运行位置       | 容差来源                                  |
| ---- | ------------------------------- | --------------------------------- | ---------------------- | -------------- | ----------------------------------------- |
| 1    | **unit**（单元测试）            | 闭式解自校验 + 边界情况，固定样本 | 无                     | `cargo test`   | 测试自述常量（铁律三）                    |
| 2    | **property**（属性测试）        | proptest 随机不变量               | 无                     | `cargo test`   | 测试自述常量（铁律三）                    |
| 3    | **golden**（金标准测试）        | 与 skrf 现算结果比对              | oracle uv 环境（skrf） | CI oracle 步骤 | manifest 按操作分档 `golden_tol`          |
| 4    | **cross-binding**（跨绑定对拍） | core/python/node/wasm 互比        | 无                     | CI             | 原生三端 bit 级；wasm `tol_rel`（铁律三） |

unit + property 在 Rust core 内，完全不碰外部；golden 锚定"与 skrf 数值一致"；
cross-binding 抓绑定层胶水 bug（字节序、形状转置、零拷贝视图错位）。

## unit —— 单元测试（解析自校验）

教科书有闭式解的电路直接手算比对。放 `core/src/**/tests.rs` 或 `core/tests/`。
容差为测试自述常量（铁律三：core 内部测试与 oracle 零依赖；跨端阅卷容差唯一
存 `oracle/manifest.json`，只服务阅卷脚本）。

### 变换恒等类

- `S → Z → S`、`S → Y → S`、`S → T → S` 往返恒等（容差为测试自述常量）
- `f → λ → f` 往返恒等与频率/波长单位换算恒等（任意合法 ε_eff，含
  DC 点 f=0 → λ=∞ 边界）——wavelength 不进横向答卷后，往返正确性与
  数值对错由此层、property 与 golden 负责
- `se2gmm → gmm2se` 往返恒等（mixed-mode）
- renormalize 到原 z0 应恒等
- `renumber` 后再按逆置换 renumber 应恒等

### 已知解析解类

- **λ/4 阻抗变换器**：闭式反射/传输直接断言
- **理想 Thru**：`S = [[0,1],[1,0]]`，级联任意网络应还原该网络
- **理想匹配负载**：`S11 = 0`
- **理想功分器 / Wilkinson**：旧库 `designer_wilkinson_splitter.s3p` 作输入
- **无损线时延**：`S21 = exp(-jβl)`，端口延时应精确抵消

### 物理不变量

- 互易网络 `S = Sᵀ`；无源网络最大奇异值 ≤ 1；无损网络 S 酉 `SᴴS = I`；
  因果性：时域冲激响应 t<0 部分能量 ≈ 0

### 编码边界（内联字节）

- latin-1 字节解码（µ = `0xB5`）、UTF-8 BOM 剥离、UTF-8 多字节注释
- 编码白名单外的名字（UTF-16、ASCII、乱码名）报错；latin-1 编码遇
  超出 U+00FF 的字符报错
- 读猜测链：UTF-8 解码失败退 latin-1（latin-1 样本喂缺省编码的
  `from_bytes`，见[I/O 边界与编码契约](#io-边界与编码契约读写动词矩阵)）

## property —— 属性测试（proptest）

随机生成**合法** Network，断言不变量；容差为测试自述常量（铁律三容差分层）。
关键属性清单：

- 参数往返恒等（S↔Z/Y/T/H/G）
- f↔λ 往返恒等（随机合法频率轴与 ε_eff）
- 级联维度正确、级联恒等（∘ Thru）
- renumber 是置换（保多重集）
- Touchstone 写出→读回恒等（bit 级）
- passivity 在级联下保持
- FFT 时域→频域往返恒等

## I/O 边界与编码契约（读写动词矩阵）

数据进出 core 只有三种边界形态，读写动词两两对称、命名同前缀（浏览器机械
camelCase 后同样整齐）：

| 边界形态 | 读                               | 写                           | 平台                    |
| -------- | -------------------------------- | ---------------------------- | ----------------------- |
| 字符串   | `from_text`                      | `to_text`                    | 全平台（纯计算）        |
| 字节     | `from_bytes(bytes, path?, enc?)` | `to_bytes(param, fmt, enc?)` | 全平台（纯计算）        |
| 文件     | `from_file`                      | `to_file`                    | `cfg(not(wasm32))` 门控 |

- **输出动词取 `to_*` 而非 `write_*`**：`from_*`/`to_*` 天然成对，`write_*` 是另起
  的家族名、与读侧不押韵。Rust 惯例本身也站在 `to_*` 一边——`to_*` = 借 `&self`
  造新值（分配、非廉价），`write_*` = 往 sink 写（`io::Write::write(&mut self)`）；
  三个动词全是 `&self`→owned，形状属 `to_*`（clippy `wrong_self_convention` 同规则）。
  同生态位实证：serde_json `to_string`/`to_vec`/`to_writer` ↔
  `from_str`/`from_slice`/`from_reader`，pandas `to_csv`/`to_json`/`to_numpy`。
  `to_text`/`to_bytes` 纯渲染不碰 I/O，用 `write_` 会让调用者误以为落盘；
  `to_*` 只说"变成什么形态"，不承诺 I/O，三档统一。
- **编码参数只进字节边界**：`from_bytes`/`to_bytes`/`from_file`/`to_file`
  带可选 `encoding`；`from_text`/`to_text` 处理的是字符串，编码无意义，不带。
- **白名单** `{UTF-8, ISO-8859-1}`，名单外（UTF-16、ASCII、乱码名）一律报错。
- **读缺省 = 猜**：先 UTF-8（含 BOM 剥离），解码失败退 ISO-8859-1；注释存
  解码后的字符串（两种编码解出的 µ 是同一个 `char`）。
- **写缺省 = 定 UTF-8**：与读"猜"的不对称系有意设计——读要兼容存量文件，
  写要最通用编码。
- **latin-1 编码在 Rust 侧完成**：JS 的 `TextEncoder` 只会编 UTF-8，
  latin-1 字节（µ→`0xB5`）只有 core 编得出；超出 U+00FF 的字符报错。
- **`write_touchstone` 改名 `to_text`**：对象已是 `Touchstone`，后缀不携带信息；
  改名同时把输出动词整体换成 `to_*` 家族。core 一处 pub fn + 三端绑定 + 测试 +
  types + README 全改，机械 camelCase 为 `toText`。未发布期改名零破坏。
- **`to_file` 的歧义可接受**：字面像"变成 File 对象"、实为写路径，与 serde
  `to_writer` 同样歧义，生态已接受；它与 `from_file` 的对仗价值大于歧义，
  混用 `write_file` 比歧义更糟。
- **`from_file`/`to_file` 对称 cfg 门控**：均 `cfg(not(target_arch="wasm32"))`；
  python/node 绑定零胶水透传。
- **浏览器 `toFile`**：core 返回 `{filename, bytes}`（已按请求编码编好的
  Uint8Array），shell 包成 `File` 返回给调用方；下载 / 剪贴板 / 另存由调用方
  决定（File 是 Blob 子类，三用途全覆盖）。core 不直接造 File/Blob：剪贴板与
  下载锚点必须在主线程且要求用户手势，worker 里的 core 躲不掉这层壳；
  MIME、lastModified 属"怎么投递"，不漏进 core。
- **浏览器另暴露 `toBytes`** → Uint8Array：用户自行决定用途（Blob、
  `ClipboardItem`、worker 传输），不经 File 壳。读侧浏览器把 File 转 bytes 喂
  `from_bytes`，写侧拿 `toBytes` 的 bytes 变 File 或进剪贴板——两方向浏览器
  只碰 Uint8Array。

**与 skrf 的偏差（有意，须记录）**：skrf `write_touchstone` 默认 ISO-8859-1，
netwave 写默认 UTF-8。后果：读 latin-1 文件再默认写回，µ 的字节从 `0xB5` 变
`0xC2 0xB5`，字节级不闭环——但 golden 轴比的是数值矩阵而非字节，samples 的
原样拷贝另有机制，故可接受；要字节闭环就显式传 `encoding`。skrf 自身同样存在
读猜/写定的不对称，属行业常态。

### golden 生成（`oracle/golden/gen_golden.py`，下期）

唯一运行 skrf 的地方，**CI 现算、golden 不入库**（铁律四）。环境 uv 管理
（`oracle/golden/pyproject.toml` + `oracle/golden/uv.lock` 钉死 skrf/numpy，
uv 工程文件住在生成侧隔离区内，不污染 oracle 根）。

- 输入样本：skrf 自带测试集（BSD-3，保留版权头）+ 旧库
  `RF-Touchstone/test/samples/`（自产 MIT）；入库逐文件登记
  `oracle/LICENSE-NOTES.md`（见 license-compliance spec）
- 覆盖操作（当前范围 = 解析 + 域/格式换算）：每个输入文件生成
  S/Z/Y/G/H 域 × RI/MA/DB 格式的数值矩阵 golden；G/H 仅 2 端口有定义，
  > 2 端口文件跳过 G/H。**文件 × 支持组合全覆盖，不挑子集**。ABCD、cascade、
  > deembed、renumber、mixed-mode、TDR 当前 netwave 不支持，对应 golden 待
  > 计算功能落地后再加
- 边界（非 50Ω）用已有文件；复数 z0 规范禁止、不造
  （见[解析覆盖契约](../openspec/specs/touchstone-core/spec.md)）
- 产物：交错复数 f64 裸二进制（小端），只活在 `oracle/tmp/golden/`，布局与
  四端答卷同构（`golden/<sample>/<family>/<variant>.bin`，golden 视作阅卷的
  第五个"端"），**不提交 git**（bin 在 git 中不可审计，维护数据变更负担
  大于收益）

### manifest.json 契约

**只放容差，不放样本名单**（铁律三；样本索引 = `samples/` 目录本身，见上节；
容差是操作的属性不是文件的属性，按操作分档）：

- `core_tol`：横向轴阅卷容差（wasm 相对容差唯一来源）；
- `golden_tol`（下期，随 golden 轴落地）：纵向轴容差按操作分档
  （如 parse / fft，铁律三默认量级）；放宽任何一档 MUST 在 manifest 注明原因；
  容差只用相对值（绝对容差在大值上误报）。

不再有的旧设计（均已废弃）：`cases[]` 逐文件清单（目录即索引，名单不再
重复维护）；`sha256` 指纹（git 内容寻址已保证 committed 文件不静默漂移，
manifest 再抄一份指纹 = 第二个真相源）；`schema_version` 字段（结构不再演进，
加容差档 = 加键）；`python_relative` 键（唯一消费者 python 绑定测试改用
自述常量，测试与 oracle 零依赖对全部端统一成立）。上述瘦身为下期实施，
当前 manifest 仍为迁入时的骨架形态。

### 阅卷集中（各端只 dump 不比较）

**目录职责分区**（oracle 根 = 契约 + 数据，脚本不平铺）：

- `oracle/` 根：`manifest.json`、`samples/`、`LICENSE-NOTES.md`——契约与数据；
- `oracle/scripts/`：阅卷侧，只准纯标准库（`compare_cross.py`、
  `compare_golden.py`、`_grading.py`、`check_samples.py`），与各子项目的
  `scripts/` 惯例对齐；
- `oracle/golden/`：生成侧，唯一允许 uv + skrf 的隔离区（`gen_golden.py` +
  `pyproject.toml` + `uv.lock`）。阅卷侧与生成侧物理隔离，
  「阅卷不碰 skrf」由结构保证而非约定；CI 也只有 golden job 需要 `uv sync`。

**答卷布局**（`oracle/tmp/`，gitignore）：

- 样本级：`tmp/<end>/<sample>/<family>/<variant>.bin`——矩阵族
  family ∈ s/z/y/g/h，格式变体 variant ∈ ri/ma/db（后缀即格式声明，
  新增变体不改目录结构）；`version.txt` 留样本层（解析元数据非矩阵，
  字符串逐字比，不转 f64——f64 会把 `1.0` 与 `1.00` 抹平，字符串更严）；
  `comments.txt` 同样留样本层（check_str 逐字比注释文本，四端注释解析与
  拼接一致）；z0 规范即实数、无格式变体，保持 `z0.bin` 平铺样本层；
- 频率轴（样本层，解析产物）：`tmp/<end>/<sample>/freq/<unit>.bin`——
  解析出的频率轴以各单位表达（Hz…THz）：文件声明单位的文件 = 解析保真，
  其余单位 = 换算，一份布局同时考频率列解析与单位换算四端一致；
  `freq/unit.txt` = 选项行单位字符串（check_str）；
- 合成轴与 wavelength 答卷退役：end 层 `freq.bin`（硬编码 1/2/5 GHz
  往返轴）是样本解析未接入时的脚手架，样本层 freq 字段在点数、单位、
  边界各维度全面覆盖它，予以废除；wavelength 不进答卷——纯数学衍生值
  的数值对错归 golden（skrf 现算）、恒等性质归 unit/property，
  其胶水路径与 freq 轴答卷完全同路，零新增覆盖，且 ε 取值无测试价值；
- 现状（已交付）为平铺 `tmp/<end>/<sample>/<field>.bin` + end 层
  `freq.bin`，family 分层、样本层 freq 字段、合成轴退役与脚本归位为
  下期迁移。

**字段注册表**：样本靠目录索引（所有样本同构处理），字段靠代码注册表——
注册表条目 field → dtype/形状规则 + 容差档 + 比对规则，阅卷按注册表逐字段
查文件，缺文件即 FAIL。目录层级只是给人看的组织，不承担索引职责。

**阅卷助手与共用库**：重复的「读四端→比对→报错」壳提成 `check`（数值，
core 为参考）与 `check_str`（字符串逐字比，version/unit 搭便车）；
`load_f64s`/`bits`/`compare`/扰动自检骨架提进 `scripts/_grading.py`，
cross 与 golden 阅卷共用，两个阅卷脚本各自只剩「组装输入 + 选容差档」薄壳。

**扰动自检随机化到字段维度**：每轮每个非参考端随机挑一个字段一个下标
扰动并要求定位——新增字段文件（如 `s/db.bin`）不可能藏成没人比的死文件。

横向轴阅卷在 `oracle/scripts/compare_cross.py`；各端测试内 MUST NOT 做
跨端比较。golden 纵向轴同理集中到 `oracle/scripts/compare_golden.py`
（下期），不在各端测试内。

### skrf 升级守护

skrf 版本靠 `oracle/golden/uv.lock` 钉死，升级 = 显式改 lock 的 PR（标准
版本化由 lock 承担）。周更 `golden-refresh.yml` workflow 作废——golden 不入库，没有
可 diff 的提交数据，不再做数据变更审计。

### oracle uv 环境落地清单（防版本漂移）

oracle 的 uv 环境（`oracle/golden/`）一落地，python 运行时与 skrf/numpy 就进了
全仓版本治理。落地时 MUST 一次改齐下表各处，漏一处即漂移：

| 位置                            | 改动                                                                                                                                                                                                        |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `oracle/golden/pyproject.toml`  | uv 工程本体（skrf/numpy 声明）                                                                                                                                                                              |
| `oracle/golden/uv.lock`         | 钉死 skrf/numpy，升级 = 显式改 lock 的 PR                                                                                                                                                                   |
| `oracle/golden/.python-version` | oracle 自己的运行时钉，与主工程同值                                                                                                                                                                         |
| `scripts/version_pins.json`     | 新增 `oracle-env`（`pin_location: oracle/golden/uv.lock`）与 `oracle-python`（`pin_location: oracle/golden/.python-version`，`paired_with: ["python-runtime"]`）条目——不登记则对账闸门的发现式扫描当场 FAIL |
| CI golden job                   | `uv sync --project oracle/golden`；`setup-python` 版本格与 oracle `.python-version` 同值                                                                                                                    |
| `scripts/check_version_pins.py` | 补跨条目版本对齐规则（见下）                                                                                                                                                                                |

**一致性兜底**：`scripts/check_version_pins.py`（离线闸门，挂在 `pnpm check:meta`）
已经管着「CI python 矩阵最新格 == `python/.python-version`」。oracle 的 python
与主工程对齐靠登记表 `paired_with` 声明——但当前闸门**只校验 `paired_with`
引用的条目存在**（防悬空名），跨条目版本相等尚未实现。oracle 落地时必须补这条
规则，否则 `paired_with` 只是文档意图、拦不住漂移。

**过期体检自动覆盖**：`pnpm check:outdated` 按发现工作——扫全仓每个 `uv.lock`
逐个 `uv lock --upgrade --dry-run`、扫全仓每个 `.python-version` 逐个与最新稳定
minor 比对打 LAG。oracle 环境落地后**无需改脚本**即自动纳入体检，契约见
[体检按发现覆盖全部环境](../openspec/changes/add-dependency-upgrade-spec/specs/dependency-upgrade/spec.md)。

## cross-binding —— 跨绑定一致性对拍

四端委托同一份 Rust 算法，断言强度按铁律三：**同机同架构原生三端 bit 级互比；
wasm 跨编译目标用 manifest 相对容差**（`core_tol.relative`，多数用例仍 bit 级
命中，SIMD 路径容差通过即正常）。CI 单 job 构建四端后跑同一组用例，阅卷在
`oracle/scripts/compare_cross.py`；本地跑法见
[CONTRIBUTING.md](../CONTRIBUTING.md) `pnpm check:cross`。

**每端答卷用该端的真实运行环境**（与各自端的单元测试同一真实性）：

- core：`cargo run` 原生；python：pytest 同环境真库；node：真 napi 产物；
- wasm 端在**真浏览器**里答卷：playwright 库脚本起 headless Chromium，
  静态服务器挂 `dist/` 与 `oracle/samples/`，页面内 `fetch` 样本 →
  `new File` → 真壳 `Touchstone.fromFile` → `toFile` 产 File →
  `URL.createObjectURL` + `<a download>` + JS 点击走真实下载路径，
  playwright `waitForEvent("download")` + `download.saveAs()` 落盘到答卷位置。
  壳的 postMessage 协议、Blob+anchor 胶水、常驻 worker 全部顺带覆盖——
  假 `self` 手搬协议的旧 dump 绕过壳层，对拍漏掉的正是壳最容易出错的胶水；
- dump 脚本只答卷不断言（阅卷集中在 `compare_cross.py`），故为 `scripts/`
  脚本而非测试文件；与 node 端对称命名 `dump.node.mjs`/`dump.wasm.mjs`，
  命令 `dump:node`/`dump:wasm`。

**端名维持 wasm**：端按编译目标命名（数值差异来自 wasm32 跨编译，非宿主），
宿主由测试配置区分（wasm config 跑 Node、browser config 跑 Chromium）；
同一 wasm 产物两宿主都跑，叫 browser 反而罩不住 Node 侧。`typescript/`
维持单一 npm 包（workspace-layout spec 钉死，exports 条件分发是 npm 生态
主流），环境分离由 `native/`+`wasm/` crate、`src/index.node.ts`+
`index.browser.ts` 双壳、`test/native|wasm|browser` 三目录与三份 vitest
config 承担，不再拆 node/browser 子目录——共享代码（types、常量、license）
无处安放，拆了更乱。

**答卷契约冻结**：拆分只换 harness，不改交卷内容——路径与字段
（`freq.bin`、`s.bin`、`z0.bin`、`version.txt`）不变，`compare_cross.py`
零改动；合成轴退役是独立任务不混入。

**全平台现场答卷、现场阅卷，不用 artifact**：wasm codegen 跨 host 工具链
不保证逐位一致（CI wasm job 即按此在每个 OS 上构建+测试），故 node job
补装 headless Chromium，`check:cross` 同场生成 wasm 答卷并阅卷；本地
`pnpm check:cross` 保持一条命令（core+python+node+wasm 答卷 + 阅卷，
缺 Chromium 时报错提示 `pnpm -C typescript exec playwright install chromium`）。

## 性能基准（criterion）

| 基准                    | 目标                  |
| ----------------------- | --------------------- |
| 解析 50MB s4p           | < 100ms（铁律六底线） |
| S→Z（1001 点 × 4 端口） | < 5ms                 |
| 级联 1000 次            | < 50ms                |
| FFT 时域 1M 点          | < 200ms               |

- CI 跑 criterion，显著劣化（>20%）失败（铁律六）；
- 大文件样本脚本生成，不提交超大文件（固定随机种子保证字节可复现、计时可比；
  具体生成参数与计时方法待实施时另议）。

### 基线跨提交持久化（Touchstone 核心期任务）

GitHub Actions runner 每次干净，`target/criterion/` 不跨 run 保留——当前 bench
job 只能测同机噪声。Touchstone 核心期改造为"基线提交进仓库"：

- CI 跑 `cargo bench -- --baseline=<仓库基线名>`，`change/estimates.json`
  导出到仓库内 `benches/baseline/` 提交（commit message 标注来源与 runner）；
- 命名空间隔离：CI 只用 `ci`，本地只用 `local`（`target/` gitignore）；
  门禁脚本只读仓库里那份 CI 基线；
- 性能变化随 PR diff 可见——与 manifest 同一套治理思路。

## 待议：过期检查升级为 CI 门禁 + bug 版本黑名单 + 登记表瘦身

三个关联问题，尚未拍板，将来专门讨论后按结论开 OpenSpec change。

### 问题一：`check:outdated` 要不要进 CI 门禁（过时即红）

**人工观点（支持进）**：把 `pnpm check:outdated` 设成 `ci.yml` 门禁，发现
过时直接报错，就能保证永远使用最新版，以后不需要人工手动升级。

**agent 观点（反对做成每 PR 门禁）**，四条理由：

1. **不可复现**：同一 commit 今天绿、明天上游发新版就红。作者没碰依赖却被
   拦，评审者无法判断 PR 本身好坏——"CI 红 = 你这个 PR 弄坏了什么"被破坏。
2. **网络抖动 = CI 抖动**：脚本要连 GitHub API / npm registry / endoflife.date
   三家，匿名限流 60 次/小时，任何一家抽风全仓 PR 陪葬。
3. **与已定选线策略打架**：dependency-upgrade spec 明确"不追 current 线、
   Python 等新 minor 且所需库全部支持才切"。若"过时即红"，Python 3.15 发布
   当天所有 PR 全红，逼人在库支持未验证时升级——违反「运行时大版本升级流程」。
4. **"永远最新"不是本仓目标**：目标是"最新稳定线 + 可复现"；追新带来的配置
   churn 正是选线原则要防的。

**折中方案（agent 建议，待人工确认）**：定时任务而非 PR 门禁——每周 cron 跑
`check:outdated`，发现 LAG 自动开 issue（或自动开 lockfile 刷新 PR）。lockfile
minor/patch 属「升级分级」中的例行刷新，机器人可代办；大版本升级涉及库支持
矩阵 + 四端对拍，MUST 走 OpenSpec change，机器人替代不了人。

### 问题二：bug 版本黑名单（配合门禁的降级豁免）

**人工观点**：门禁化后必然遇到"最新版有 bug 必须降级"的情况，应把有 bug 的
版本另存一处，检查时跳过它。

**agent 观点（同意机制，反对另存一处）**：另存 = 第二个真相源，必与登记表
漂移。落法：给 `scripts/version_pins.json` 条目加字段——

```json
"blocked": [{"version": "1.2.3", "reason": "upstream bug", "issue": "https://..."}]
```

`check_outdated.py` 读到 latest 命中 blocked 即改报"目标 = 次新版"。黑名单
条目本身就是「回退须证据」的机器可读载体（issue 链接 + 理由随条目入库），
bug 修复后删条目 = 回归升级，追溯靠 git log。

### 问题三：登记表 json 是否还有必要（发现式扫描能否取代）

**人工观点（json 可砍）**：`check_version_pins.py` 已能发现式扫描全部钉版文件，
直接把所有文件的版本号拉出来互相比对，相同即过、不同即红；再用
`check_outdated.py` 查是否最新——任务同样完成，且不会遗漏文件，那 json 还有
什么存在必要？

**agent 观点（json 保留，但可瘦身）**：纯"值一致性"层面人工说得对——检查
3/4/6/7 全是"发现→比对"模式，本就不依赖 json 的文件列表。但 json 里有三样
**扫描文件扫不出来的知识**：

1. **升级方法（程序性知识）**：如 rust-toolchain 的 `upgrade_method` 记录"升
   channel 后要补装 rustfmt/clippy 组件 + wasm32 target + 重装 cargo 子命令
   （rustup 不自动做）"。文件本身只写 `channel = "1.99.1"`，不会告诉你升级它
   要连带干哪四件事——这是踩坑换来的步骤，砍掉 json 就只能散进散文或注释，
   正是登记表要消灭的"散落副本"。
2. **配对关系（语义知识）**：napi-cli↔napi crate、pyo3↔numpy、
   wasm-pack↔binaryen 必须联动升级。扫描能发现两个文件各有一个版本号，但无法
   知道它们是一对（上游生态约定，只存在于文档/人脑）；`check_outdated.py` 只会
   分别报两个落后，不会报"这俩必须一起动"。
3. **机器环境钉（不在仓库文件里）**：rustup、node、uv、openspec、playwright
   浏览器钉在开发机上，仓库无任何文件承载。若砍 json，`check_outdated.py` 里
   那张 `cli_checks` 硬编码表就成了唯一登记处，反把最该集中管的知识塞进脚本。

另有一处反例：若"拉出所有文件的所有版本号"扫描，`typescript/package.json` 里
几十个 devDependencies 全是版本号——哪些是治理级结构钉（typescript↔tsdown
配对）、哪些是普通依赖（lockfile 例行刷新管）？扫描区分不了，这个区分正是 json
的 `category` + 条目选择本身。

**瘦身方向（agent 建议，与人工"砍 json"方向相反地用）**：不是"json vs 发现"，
而是分工——发现式扫描管值一致性与未登记检测（不需要 json 的文件列表）；json
只存**发现不了的东西**（upgrade_method、paired_with、machine: 条目、底线语义）；
check_outdated.py 管新旧。据此 json 现有可删冗余：`rust-msrv` 的四个文件列表、
ci-actions 的 watch 列表——扫描已能发现，json 再抄一份位置清单 = 第二真相源。
瘦身后条目只留"名字 + 类别 + 升级方法 + 配对"，位置由扫描提供（machine/全局
条目除外）。

### 落地形态（三问合并）

改动触及契约：「过期体检命令」的 MUST NOT 进 CI 条款（改为"定时可进、PR 门禁
不进"）、登记表 schema（加 `blocked`、删位置清单冗余）、新增 workflow——属结构性
升级，MUST 单独开 OpenSpec change（暂名 `add-freshness-schedule-gate`），待上述
三问拍板后 propose。

## 覆盖率标准

**全端 100% 行覆盖，unit 层零豁免**（铁律七）；唯一例外为结构性不可达代码，
逐条标注豁免并登记理由（stable 通道 `#[cfg(not(coverage))]` / `# pragma: no cover` /
`/* v8 ignore start/stop */`；`#[coverage(off)]` nightly-only 禁用），禁止整文件/整目录批量豁免。工具与门槛：
`cargo llvm-cov -p netwave`、`pytest-cov`、vitest v8 `lines/branches: 100`、clippy、fmt。
具体命令行见 [CONTRIBUTING.md](../CONTRIBUTING.md) 与各子 README。

100% 是**下限不是目标**：执行到 ≠ 断言对，数值正确性由 golden/property/
cross-binding 负责。
