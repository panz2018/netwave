## 登记表 schema 重构（探讨，未拍板）

> 针对 `scripts/versions/lib/registry.json`（31 条 pin 平铺）的"太复杂、
> 命名乱、需要地址化"问题。拍板后按 governance 开 OpenSpec change 实施。
> 与下文"scripts/versions 拆包"是两回事：本节动**数据 schema**，
> 那节动**代码分层**，可先后独立做（倾向先 schema，见待决问题）。

### 问题诊断：一条 pin 扛了五种职责

```text
+---------------------------------------------------------------+
| 一条 pin =                                                      |
|   身份    name（"python-runtime"）                              |
|   位置    pin_location + field（钉在哪个文件哪个字段）            |
|   分类    category（13 类枚举）                                 |
|   政策    upgrade_method / verified（怎么升、验过什么）           |
|   关系    paired_with / blocked（跟谁联动、哪些版本坏）           |
+---------------------------------------------------------------+
```

31 条平铺一个数组，五种性质不同的信息横向穿插——"复杂感"的根源不是条数多，
是每一行都在换话题。

### 命名硬伤清单

| 症状                               | 例子                                                                                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 词序不一致（领域前 vs 位置前混用） | `python-runtime` vs `root-python`；`python-requires` vs `root-requires`                                                                             |
| 边被起了节点的名                   | `typescript-tsdown-pair` 实为 typescript 的 pin、`napi-pair` 实为 @napi-rs/cli 的 pin；"pair" 是关系却占了条目名，真正的关系 `paired_with` 反而无名 |
| 位置表达是伪地址                   | `field: "dependencies.pyo3, dependencies.numpy"`——逗号拼字符串，不可解析                                                                            |
| 一条扛全部                         | `ci-actions` 单条代表 workflow 全部 action，blocked 无法挂到具体 action                                                                             |

### "地址化"的两层含义（待拍板）

- **定位地址化**：把"钉在哪"从 `pin_location` + `field` 两个松散字段，变成
  结构化地址 `文件 + 文件内指针`（如
  `typescript/package.json → devDependencies.@napi-rs/cli`），闸门可直接
  解引用，不再靠 `field` 字符串约定与特判正则。
- **引用地址化**：条目间引用（`paired_with`、pairs 的 a/b、blocked 的
  issue）不写裸名字，写可跳转地址（如 `#pins/python-runtime`），改名/删条目
  时断链当场暴露，人也能一键跳到对方定义。

### 拆分候选（选轴不选刀）

| 候选           | 做法                                                                                             | 代价                                               |
| -------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------- |
| 单文件内分表   | `pins`（位置+分类）/ `pairs`（关系边）/ `blocked`（黑名单）三表                                  | 最小；spec 波及小                                  |
| 按域拆多文件   | `toolchain.json`、`languages.json`、`deps.json`、`machine.json`…                                 | "唯一真相源"变"一个目录"，发现式扫描与对账口径重定 |
| 命名层级地址化 | 条目名改 `域.对象`（`rust.toolchain`、`python.runtime`），名字即地址，引用统一 `@rust.toolchain` | 31 条全改名 + 全部引用点波及                       |

### 当前倾向（未拍板）

**单文件内分表 + 命名层级地址化**：pairs 独立本就在下文配对校验内，
顺手把 blocked 提成独立表；按域拆多文件会把刚收拢的结构重新打散，
与"先收结构不动行为"的既定口味相悖。

### 待决问题

- "地址化"取定位、引用两层中的哪层，还是都要（决定 schema 改动幅度）。
- 层级命名 `域.对象` 是否连 `category` 一起吸收（名字前缀即类别，
  category 字段或可废——但 category 现有 13 类与"域"不是一刀切的映射）。
- `ci-actions` 要不要拆成逐 action 条目（拆了才能挂 blocked，但条目数膨胀）。
- 边与节点分离后，`typescript-tsdown-pair` 这类"名字带 pair 的节点"归位：
  节点留 `pins`、边进 `pairs`，一次改名到位。
- 与拆包的先后：先改数据 schema 再拆代码，还是反过来（倾向先 schema，
  拆包时按新 schema 设计模块接口，避免拆完再返工）。

## 配对版本校验（最小方案，方向已对齐）

> 研究问题：`scripts/versions/lib/registry.json` 的 `paired_with` 目前只校验
> "配对名字存在"，不校验"配对双方版本是否相容"。本文逐对核实每条配对边的
> **真实约束语义**与**可机检性**，给出最小落地思路：**接口一次定死，
> 能确定的约束先填，不确定的留空位、升级踩到再补**。

### 大白话结论（先读这段）

方向已与人工对齐，走最省事的路线：**接口一次定死，能确定的约束现在填，
不确定的留空位，升级踩到问题再往里补**。

- 登记表加一张 `pairs` 表，每条边声明一个约束词；词表封闭，只有四个：
  `eq`（相等）、`eq_major`（major 相等）、`le` / `ge`（不大于 / 不小于）。
- 只填**现在就能确定**的边（MSRV ≤ toolchain、runtime ≥ floor、CI 矩阵 ≥ 底线、
  napi-cli ↔ napi 同 major、pyo3 ↔ numpy 同 major）。
- 语义不明确的边（pyo3 支持到哪个 Python、pnpm/napi-cli 跟 node 的关系、
  wasm-pack ↔ binaryen 等）**不强行找约束**，继续留在 `paired_with` 里当
  升级联动提醒；将来哪条明确了，往 `pairs` 加一行即可，接口不动。
- 闸门按声明执行：读两侧当前值、按词比较、违反即 FAIL。

### 现状：闸门到底查了什么

`scripts/versions/check_versions.py` 对 `paired_with` 只做一件事——结构检查末尾的"悬空名
校验"：每个 `paired_with` 引用的条目名必须在登记表里存在。**不读任何版本号、不
比较任何配对**。所以 `python-runtime`(3.14) 与 `python-requires`(>=3.10) 这对，
闸门知道"它俩是一对"，但即使把 runtime 改成 3.9（低于 floor）也不会 FAIL。

更关键的隐藏缺口：`current_values()`（闸门里"从仓库文件读当前钉版值"的函数）
**只读得懂这几种值**——`rust-toolchain.toml` channel、`packageManager`、
`.python-version`、CI workflow 里的 `python-version:`/`node-version:` 矩阵格、
全 pin 的 action tag、`discovered:` 规则发现的成员 MSRV。它**读不出**
`pyproject.toml` 的 `requires-python`、`package.json` 的 `engines.node`、
`devDependencies` 里的具体版本、`Cargo.lock` 里解析出的 crate 版本。也就是说，
即便现在想加配对校验，多数配对边的"值"根本还没被抽出来。这是落地的真正前置工作，
不是写个比较函数那么简单。

### 最小方案（当前思路）

**接口一次定死，内容按需增量**：登记表顶层加 `pairs` 表，闸门按表
执行；将来新增配对只是加一行数据，接口和闸门代码不再动。

#### 约束词表（封闭，四个）

| 词         | 判定                        |
| ---------- | --------------------------- |
| `eq`       | 两侧版本完全相等            |
| `eq_major` | 两侧 major 相等（lockstep） |
| `le`       | a 的每个值 ≤ b 的每个值     |
| `ge`       | a 的每个值 ≥ b 的每个值     |

`b` 省略表示"同一条目内部各值互比"（如 `pyo3-numpy-pair` 的 field 列两个依赖）。

#### 现在就能确定的边（先填这些）

```jsonc
// scripts/versions/lib/registry.json 顶层新增
"pairs": [
  { "a": "rust-msrv", "b": "rust-toolchain", "constraint": "le" },
  { "a": "python-runtime", "b": "python-requires", "constraint": "ge" },
  { "a": "ci-python-matrix", "b": "python-requires", "constraint": "ge" },
  { "a": "ci-node-matrix", "b": "node-engines", "constraint": "ge" },
  { "a": "napi-pair", "b": "napi-crate", "constraint": "eq_major" },
  { "a": "pyo3-numpy-pair", "constraint": "eq_major" }
]
```

#### 闸门行为（`check_versions.py` 扩展）

- 取值：现有 `current_values()` 补三类 reader——`pyproject.toml` 的
  `requires-python`、`package.json` 的 `engines.node` 与 devDependencies 具体版、
  `Cargo.lock` 指定 crate 的解析版；比较符（`>=`、`^`、`~`）剥掉再比。
- 判定：按约束词比较两侧值，违反即 FAIL 并点名两侧来源。
- **只注册"值可读"的边**，所以读不到值 = 登记表漂移 = FAIL，不搞静默跳过
  （比宽松版更严也更简单）。
- `pairs` 是 `paired_with` 的子集：闸门顺手校验每条 pair 的两端在 `paired_with`
  里声明过，防两表漂移；`paired_with` 继续承担"升级联动提醒"职责。

#### 不确定的边：留空位，踩坑再补

pyo3 支持到哪个 Python、pnpm/napi-cli 跟 node 的关系、wasm-pack ↔ binaryen、
typescript ↔ tsdown（安装期 `pnpm peers check` 已兜住）等，**现在不强行找
约束**。它们留在 `paired_with` 里；将来升级真碰到不兼容，把确认下来的语义写成
一行 `pairs` 边即可——接口不用改。oracle 落地时加
`{ "a": "oracle-python", "b": "python-runtime", "constraint": "eq" }`
是同一个动作。

### 待继续讨论

1. 词表四个够不够（`floor_eq` / `in` 是否永远可用 `ge` + 现有泛查替代）。
2. `pnpm peers check` 要不要接进 `check:meta`（接了 peer 类边全部白送，
   代价是 `check:meta` 从此依赖 pnpm 与 lockfile 在场）。
3. spec 波及：dependency-upgrade「登记条目结构完整」要补 `pairs` 结构描述，
   随实施开 change 还是豁免。
4. 现有散码一致性规则（MSRV `le`、`.python-version` ∈ 矩阵泛查）是否收编进
   `pairs` 表达（不阻塞：新旧并存不冲突）。

核实依据（关键几条，可复核）：

- tsdown 的 peer 范围：`pnpm-lock.yaml:2216`（`typescript: ^5.0.0 || ^6.0.0 || ^7.0.0`），
  当前 typescript 7.0.2 满足——所以这对**今天不报错**，但 package.json 里看不到
  这个范围，只能从 lockfile 或 registry 读，故归 `peer` 类而非离线 `range`。
- pyo3 对 Python 上限属上游声明：pyo3 0.30.0 CHANGELOG 才加 "Support Python
  3.15.0 final"（[PyO3 CHANGELOG](https://raw.githubusercontent.com/PyO3/pyo3/main/CHANGELOG.md)，
  PR #6517）；当前 0.29 不支持 3.15。这类"谁支持谁"无法离线算，必须联网查上游。
- `pnpm peers check` 退出码实测：peer 全满足退 0、有 unmet 退 1（`--strict` 退 2），
  且读 lockfile 不联网——是现成的、机器可读的 peer 闸门。本仓根目录当前退 0
  （`No peer dependency issues found`）。
- `uv lock --locked` 离线断言 lock 与 pyproject 一致，实测退 0——是现成的
  "uv.lock ↔ python 声明"一致性闸门，无需自造。
- pnpm `engines.node`、`@napi-rs/cli` `engines.node` 取自 npm registry 对应版本
  的 `engines` 字段（`>=18.*`、`^20.17.0 || ^22.13.0 || >= 23.5.0`）。

### 生态现成做法（先查再提，避免重造）

"声明式配对约束 + 安装器/解析器校验"是各包管理器的标准能力，netwave 不是发明新
机制，而是把同一思路用在**包管理器罩不住的跨工具钉版点**上：

- **npm/pnpm/yarn**：`peerDependencies` 声明"我要求某包在某范围"，
  `peerDependenciesMeta` 标可选；安装器校验，pnpm 另给 `peers check` 命令
  （实测退码见上）。这是 `peer` 约束词的现成原型。
- **cargo**：`[dependencies]` 的版本请求 + `Cargo.lock` 解析真相；`cargo tree -d`
  查重复版本。`eq_major`（pyo3↔numpy、napi-cli↔napi）本质是"同一 crate 树里
  major 必须一致"，cargo 解析已保证，闸门只是把"升级方法里写的 same-major"变成
  机器断言。
- **Python/PEP 440**：`requires-python` 与依赖的版本说明符；uv `--locked`/`--frozen`
  断言 lock 不漂移（实测可用）。`ge`/`floor_eq` 就是 PEP 440 说明符的子集。
- **endoflife.date / nodejs.org dist index**：`upstream` 类（谁支持到哪个版本）的
  权威数据源，`check_outdated.py` 已在用。

结论：约束词不必自造语义，每个词都对应一个成熟生态机制；netwave 的增量只是
"跨 rust-toolchain / CI 矩阵 / .python-version / lockfile 这些不同文件之间的
配对"没有现成工具，需要一张登记表 + 一个按声明执行的薄闸门。

## 过期检查门禁化（`check:outdated` 要不要进 CI 门禁，待拍板）

**人工观点（支持进）**：把 `pnpm check:outdated` 设成 `ci.yml` 门禁，发现
过时直接报错，就能保证永远使用最新版，以后不需要人工手动升级。

**agent 观点（反对做成每 PR 门禁）**，四条理由：

1. **不可复现**：同一 commit 今天绿、明天上游发新版就红。作者没碰依赖却被
   拦，评审者无法判断 PR 本身好坏——"CI 红 = 你这个 PR 弄坏了什么"被破坏。
2. **网络抖动 = CI 抖动**：脚本要连 GitHub API / npm registry / endoflife.date
   三家，匿名限流 60 次/小时，任何一家抽风全仓 PR 陪葬。
3. **与已定选线策略打架**：dependency-upgrade spec 明确"不追 current 线、
   Python 等新 minor 且所需库全部支持才切"。若"过时即红"，Python 3.15 发布
   当天所有 PR 全红，逼人在库支持未验证时升级——违反「运行时大版本升级流程」。
4. **"永远最新"不是本仓目标**：目标是"最新稳定线 + 可复现"；追新带来的配置
   churn 正是选线原则要防的。

**折中方案（agent 建议，待人工确认）**：定时任务而非 PR 门禁——每周 cron 跑
`check:outdated`，发现 LAG 自动开 issue（或自动开 lockfile 刷新 PR）。lockfile
minor/patch 属「升级分级」中的例行刷新，机器人可代办；大版本升级涉及库支持
矩阵 + 四端对拍，MUST 走 OpenSpec change，机器人替代不了人。

**安全阀（门禁化 change 的备查要求）**：任何自动化提议升级（机器人开 issue /
刷新 PR）MUST NOT 推荐登记表 `blocked` 清单中的版本——黑名单已由
`check_outdated.py` 消费（见 dependency-upgrade spec 坏版本黑名单），
门禁化实现时直接复用其过滤结果，禁止另造第二套判断。

**落地形态**：改动触及契约——「过期体检命令」的 MUST NOT 进 CI 条款（改为
"定时可进、PR 门禁不进"）、新增 workflow——属结构性升级，MUST 单独开
OpenSpec change（暂名 `add-freshness-schedule-gate`），待拍板后 propose。

## scripts/ 治理待议（单测覆盖率 / 目录命名 / 脚本自身升级）

`scripts/` 现在有 10 个平铺 py 闸门 + 2 个 sh 安装脚本 + `versions/` 包，
黑名单落地后复杂度又上一台阶。三个关联问题尚未拍板，将来专门讨论后按结论
开 OpenSpec change。本节只存正反双方论点与待决点，不预设结论。
已拍板不再讨论：独立 uv 工程——仓库根 `pyproject.toml`（private，
dev 组 pytest/pytest-cov/ruff）已建，契约见
[workspace-layout 根级 Python 工具环境](../openspec/specs/workspace-layout/spec.md)。

### 要不要单元测试 + 覆盖率 100%

**正方（要，且 100%）**：

- 闸门 bug 的后果是**静默放行**（该 FAIL 的输入被放过），比业务代码 bug
  更隐蔽——业务代码错了测试会红，闸门错了没人知道它没拦；
- 闸门是"守门员"，守门员自己没测试体系（无 pytest、无覆盖率），
  与 `python/` 工程的待遇不对等；
- 铁律七本来就要求全端 100% 行覆盖 unit 层零豁免，闸门脚本是仓库代码，
  没有理由例外；
- 黑名单、发现式扫描、slug 规则、版本比较这些纯逻辑分支多，手工 red/green
  验证（黑名单实施即如此）不可回归，改一次闸门就得手测一轮。

**反方（要测试，但 100% 一刀切不对）**：

- 脚本里大量代码是**网络与子进程胶水**（`_req`、`run`、GitHub/npm/
  endoflife 三家 API、pnpm/cargo/uv 子进程），逐行覆盖它们只能靠打桩，
  桩测出来的"绿"不证明真环境能跑，反而制造虚假安全感；
- 覆盖率数字对这类工具意义有限：真正危险的是**规则漏判**（该拦没拦），
  这是用例设计问题，不是行覆盖率问题；
- 铁律七的豁免机制（结构性不可达逐条标注）本就为此设计，硬凑 100%
  会催生无断言的"刷覆盖"测试。

**折中（agent 建议，待人工确认）**：纯逻辑（登记表结构校验、精确版本
正则、blocked 匹配、发现式扫描、markdown 链接/slug 规则、`_semver`
比较、bench/coverage 阈值判定）100% 行覆盖 + 关键分支用例；网络/子进程
胶水段打桩测"调用形状"，异常分支按铁律七逐条 `# pragma: no cover` 标注
豁免，禁止整文件排除。

**待决点**：pytest 挂进哪条闸门（`check:py` 追加、还是新命令
`check:scripts`）；进不进 `check:meta`；覆盖率是否进 coverage_gate。

### 目录命名（scripts / manage / control）

**正方（改名 manage/ 或 control/）**：

- "scripts" 太泛，不表达"治理工具集"的身份；manage/control 更点题。

**反方（留 scripts/）**：

- `scripts/` 被钉死在：根 `package.json` 全部命令、`ci.yml`、登记表
  `pin_location`、AGENTS/CONTRIBUTING/scripts README、workspace-layout
  spec、install 脚本互引——改名波及面全仓，收益只有"好看"；
- "管理入口"职责已有归属：根 `package.json` 的 `check:*`/`fix:*` 就是
  门面，AGENTS.md 明文"对称命令以根 package.json 为唯一定义处"；
  再造 `manage.py` 调度器 = 第二个命令真相源，必漂移（违反登记表
  唯一真相源的同款理由）；
- 命名是名字不是契约，位置语义靠 README 表达即可。

**待决点**：无强烈改名动机，倾向维持；若改，必须与结构收编合并成一次
结构性 change，禁止单独折腾。

### 脚本自身的升级管理

**现状（反方认为无需新机制）**：脚本升级 = 改代码本身，走现有闸门 + git
即可；脚本依赖的外部工具版本（ruff/pytest）由根 `uv.lock` 管，
`check:outdated` 已覆盖；脚本调用的上游工具链由 dependency-upgrade spec
全套机制管。没有缺口。

**正方（仍有可议空间）**：闸门之间有无执行顺序依赖（如 check:meta 内
六闸门顺序）是否需要显式声明与对账；脚本内硬编码的 URL/正则（如
endoflife cycle、npm dist-tag）有无"过期"概念需要体检。
