# 脚手架自由函数退役

`fill_pattern` / `read_element` 这类**模块级自由函数**目前仍挂在 core 与
node/Python 公开面上。本 change（`unify-drop-verb-and-class-surface`）的
proposal 第一条 BREAKING 已写明「脚手架自由函数面收进类骨架」，活 spec 的
[有状态对象用类、无状态变换用模块函数](../openspec/specs/api-contract/spec.md#requirement-有状态对象用类无状态变换用模块函数)
也只保留 `frequencyUnits()`/`liveCount()` 两个无状态自由函数。但 tasks.md
没把「删自由函数」拆成可执行条目，本文件补齐待办与波及面，等拍板后立项执行。

## 问题

`Network` 类落地后，`fill_pattern` 的配方（closed-form 图案）在
`core/src/network.rs` 的 `Network::fill_pattern` 里已由
`crate::fill_pattern` 委托取得。自由函数与类方法**同一配方两份入口**，
与「公开面收进类骨架」的定案不符。

## 难点：零拷贝视图与 `drop()` 的内存安全张力

node/Python 的自由函数不只是便捷入口，它们是**零拷贝的活证据**：

- Python `fill_pattern` 返回 `owndata=False` 的 ndarray（内存 owner 是
  Rust `Owner`，作 base object 挂在数组上）；`read_element(arr, idx)` 把
  视图**传回** Rust 按指针读，证明「Python 写入 == core 内存」。
- node `fill_pattern` 返回零拷贝 V8 external `Buffer`；
  `_readElement(view, idx)` 同理把 Float64Array 传回 Rust 读。

自由函数一删，整块零拷贝出口必须落到 `Network` 实例上。真正的难点不是
「有没有出口」，而是 `Network` 同时带 `drop()`：`toBuffer()` 把内存地址交给
JS 视图后，若 `drop()` 立即 `Vec::new()` 释放，视图就成了悬垂指针，且 JS 侧
GC 回收视图时会对同一地址二次释放。解法是引用计数——见
[实现方式](#实现方式)。此难点只存在于**同进程共享内存的 Python/node 端**；
浏览器端走 transfer 所有权移交，无共享、无悬垂，难点不同（worker 表钉死
对象致泄漏），见[浏览器端](#浏览器端跨线程无共享)。

## 已定

1. **退役时机**：随本 change 一并做，`toBuffer()` 同批落地承接零拷贝证据，
   不再推迟到 Touchstone 核心立项。
2. **零拷贝证据**：整块视图零拷贝断言由 `toBuffer()` 承载，不退化为逐元素抽查。
3. **裸视图入口**：`read_element(view, idx)` 与逐元素 `readElement(idx)` 一并删除，
   读写整块统一走 `toBuffer()` getter / `buffer` setter。

## 实现方式

公开面收口后，整块零拷贝出口与 `drop()` 共存靠**引用计数 + 回收回调**，
不靠拷贝、也不靠「不存指针」。

### 公开面

| 动作 | 名称                                           | 说明                                                                      |
| ---- | ---------------------------------------------- | ------------------------------------------------------------------------- |
| 删   | `fill_pattern` 自由函数                        | 配方收进 `Network::fill_pattern`                                          |
| 删   | `read_element(view, idx)` / `readElement(idx)` | 裸视图与逐元素入口一并退役                                                |
| 增   | `toBuffer()` getter                            | 返回整块零拷贝视图（node `ArrayBuffer`/`Float64Array`、Python `ndarray`） |
| 增   | `buffer` setter                                | 整块写入：换一整块新 `Arc`，形状随参数更新；浏览器端经边界拷贝进 worker   |
| 留   | `fillPattern` / `drop` / `nfreq` / `nports`    | 工厂、释放、形状读取不变                                                  |

### 内存机制分端总览（先分清三种情况）

| 端                        | 数据共享方式                                             | 要不要 Arc                                      | `drop()` 的角色                                                                                | 释放通道                                                        |
| ------------------------- | -------------------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Python / node             | 同进程共享同一块内存（零拷贝视图）                       | **要**：`Arc<Vec<f64>>` + GC 回收回调           | 封存实例 + 撒自己那把钥匙；物理内存随最后一个视图散场                                          | 手动 `drop()` 或实例 RAII；视图归对面 GC                        |
| 浏览器（worker）          | **无共享**：结果 buffer 经 transfer 整体移交，主线程独占 | **不要**：无共享即无悬垂，Arc 无用武之地        | **唯一释放通道**：JS GC 够不着 wasm 堆，不发消息 `remove(handle)` 则 worker 表钉死对象、纯泄漏 | 壳被 GC → registry 发 `{handle, method:"drop"}` → core `remove` |
| 未来计算值（toS/toY/toZ） | 算完整块交出，Rust 不留副本                              | **不要**：新分配新 buffer 直接归对面 GC，无共享 | 对它无事可做（不在 Rust 手里）                                                                 | 对面 GC 直接 free                                               |

### 同进程端（Python/node）：引用计数

- core：`Network.data` 由 `Vec<f64>` 改 `Arc<Vec<f64>>`。
- `toBuffer()`：`Arc::clone`（计数 +1），把裸地址 + 回收回调交给绑定层，
  **不复制字节**。`Arc::clone` 不复制数据——只在堆上计数器 +1、多配一把
  「钥匙」，与数据大小无关。
- `drop()`：Network 撒手（计数 -1）+ 置 `dropped`，实例侧访问报错；
  **只撒自己那 1 把，已借出视图各拿各的钥匙、各减各的**，故只要还有视图
  未回收，物理内存不释放，不悬垂。
- 视图被 GC：回收回调 drop 那个 `Arc` clone（计数 -1），最后一个撒手才 free。
- **多 buffer 字段（未来 S/Y/Z 等）零手写计数**：每个 `Arc` 字段自带
  「我死了我的计数 −1」，`drop()` 清空字段或实例被回收时 Rust RAII 挨个
  自动减；加一个 buffer = 加一个字段，不增加任何计数代码。
- `buffer` setter（换指针语义）：`self.data = Arc::new(新数据)` + 形状随
  参数更新（长度可变）。**已借出的旧视图不悬垂、仍可正常读**——旧 Arc 被
  视图续着，它看到的是写入前的旧数据快照；此后 `toBuffer()` 返回新数据。
  测试须显式断言「set 后旧视图=旧快照、新视图=新数据」。

### 三家实证（同生态成熟做法）

- arrow-rs `arrow-data/src/ffi.rs`：`Arc<Buffer>` + FFI `private_data`，
  消费方 `Drop` 调 `release` 回调 `Box::from_raw` 精确释放一次。
- napi-rs `crates/napi/src/bindgen_runtime/js_values/arraybuffer.rs`：
  `ArrayBuffer::from_external` + `mem::forget`，V8 GC 调 finalize 回调
  `Vec::from_raw_parts` 回收；仅 `napi_no_external_buffers_allowed`
  （electron）才退化为 `copy_from`。
- rust-numpy `src/array.rs`：`PyArray::borrow_from_array(arr, owner)`，
  owner 挂成 numpy `base`，numpy 保证 base 比视图活得久。

`mem::forget` / `Box::into_raw` **不删**——它们是「把所有权交给对面 GC」的
动作，删了 Rust 会在函数返回即回收，视图当场悬垂。安全来自「GC 回收时回调
进 Rust 精确释放一次」，不来自「不存指针」。

### 浏览器端（跨线程，无共享）

- 计算结果 buffer 以 `postMessage(buffer, [buffer])` **transfer** 整体移交
  （铁律八）：V8 直接移交底层内存所有权，零字节拷贝，原 buffer 当场
  detached。主线程独占该 buffer，归 JS GC 管——**没有共享，就没有 Arc 的
  用武之地**。
- `toBuffer()` 在浏览器端返回 worker 新分配并 transfer 回主线程的 buffer
  （非共享视图），语义与同进程端「同一块内存」不同，接口签名一致
  （zero-copy-roundtrip spec「await 后必须重建视图」）。
- `drop()` 在浏览器端**不可删**：wasm 线性内存对 V8 GC 是一整块不透明
  字节，worker 资源表里的 `Box<Network>` 没人 `remove(handle)` 就永远钉在
  表里（纯泄漏，与悬垂无关）。释放链唯一：壳被 GC → `FinalizationRegistry`
  回调 → `postMessage {handle, method:"drop"}` → core `remove` → Rust
  `Drop`。改名成 `free`/`release` 也还是它（且二者是 `check_verbs.py`
  禁词）。
- 浏览器端 `buffer` setter 仍存在（三端动词集必须相等，铁律十二），但实现
  是**边界拷贝**进 worker 再换 Arc——不消耗调用方视图（zero-copy-roundtrip
  spec「边界拷贝进入 worker」允许；只有 `upload`/`drop` 这类名字明说移交的
  才 transfer 输入）。`upload` 语义不变：transfer 移交、原视图 detached。

### 与 memory-lifecycle 的张力（已定案）

`toBuffer()` 视图持 `Arc` clone 续命，与
[memory-lifecycle](../openspec/specs/memory-lifecycle/spec.md)「显式 `drop()`
确定性即时」存在边界张力，定案如下：

- **`drop()` 三端保留**：浏览器端它是唯一释放通道（删了必泄漏），铁律十二
  要求三端同名，故动词表不动。Python/node 端 Arc 已兜底内存安全，`drop()`
  的价值改述为「确定性封存实例（访问立即报错）+ 撒自己那把钥匙」，不再
  承诺「立即释放物理内存」——memory-lifecycle spec 出 delta 改这条
  requirement 的措辞（「即时」限定于实例封存，物理内存随最后一个视图
  散场）。
- **`live_count()` 保持 `Frequency` 专属，不扩到 `Network`**：该计数器现只
  数 `Frequency`（定义于 `core/src/frequency.rs`，全部测试也只见证
  `Frequency`）。`Frequency` 需要计数器是因为其契约「Rust `Drop` 真跑了」
  肉眼不可见；`Network` 的契约是「drop 后实例立即封死」，见证手段就是
  **访问报错本身**（`dropped` 标志），测试直接断言报错，零新代码、不加新
  计数器。「drop 不依赖 GC 即时回收」scenario 对 Network 以报错断言成立。
