# NetWave 总体计划

> 一个频域散射矩阵（S-matrix）电路求解引擎，Rust 高性能核心 + Python/TypeScript 双端零拷贝绑定，
> 同一套程序同时服务 RF 与光学（光子学）。

## 项目定位

- 本质是**频域散射矩阵线性网络求解器**：RF 与光子学的 S 参数在数学上是同一对象
  （端口复数相量 + 散射矩阵），引擎**域无关**，只做频域、基于 S-parameter，不做时域仿真。
- 要解决的问题：旧纯 TS 实现（`RF-Touchstone`）用 `mathjs` 的 `Complex[][][]`
  对象数组做计算，大 Touchstone 文件（>50MB）直接卡死；缺 Network/Circuit 体系；
  无 Python 端能力。
- 命名：**netwave**（network + wave）；核心类型不出现 `rf` 前缀，`z0` 是端口属性
  （[铁律五](../openspec/specs/project-governance/spec.md)）。

## 已定案架构（正文已迁入 spec，此处只留结论与指针）

- **Rust 核心 + 三端零拷贝绑定**（PyO3/napi-rs/wasm-bindgen）：Rust 是唯一在
  Python/Node/浏览器三目标都有一线零拷贝绑定工具链的语言。
- **数据布局**：`(nfreq, nports, nports)` 交错复数扁平 f64，与 skrf `Network.s`
  逐字节相同——[铁律一](../openspec/specs/project-governance/spec.md)。
- **跨语言 API 面三层契约**（数据/计算/结构）、类式 API 形态、`upload`/`drop`、
  z0 双动词、频率轴 f64 Hz、结构变更语义、worker 泛化分发——
  [api-contract spec](../openspec/specs/api-contract/spec.md)。
- **仓库结构与发布名解耦**：平铺 monorepo（core/python/typescript/testdata），
  三注册表主名一律 `netwave`，npm 单包 exports 条件分发——
  [workspace-layout spec](../openspec/specs/workspace-layout/spec.md)。
- **版本底线与 CI 矩阵**：Rust edition 2024 / Python ≥3.10 / Node ≥22——
  [workspace-layout spec](../openspec/specs/workspace-layout/spec.md)「版本底线」；
  矩阵见 [ci-matrix spec](../openspec/specs/ci-matrix/spec.md)。
- **包管理**：Python 一律 uv、Node 一律 pnpm（禁裸 pip/npm/yarn）；命令与坑见
  [CONTRIBUTING.md](../CONTRIBUTING.md) 与各子 README。
- **GPU（WebGPU/WebGL/CUDA）已评估，任何端都不引入**：f64 不支持违反铁律一、
  小矩阵负载不匹配、破坏零拷贝、生态冲突（论证全文见 git 历史本文件旧版）。
  WebGL 在 viewer 中只允许渲染不计算。将来重开 GPU 唯一合理场景是
  原生端大规模矢量拟合（Python 侧 CuPy），与浏览器无关。
- **旧库 `RF-Touchstone` 不做兼容层**：README 指向 netwave + 迁移对照表后归档
  （见[功能覆盖规划](功能覆盖规划.md)）。
- **多线程 wasm（wthreads + COOP/COEP）为可选增强**：运行时检测
  `crossOriginIsolated` 否则单线程回退；见[路线图](#路线图)「wasm 性能定标与提速」。

## 功能范围（对标 scikit-rf / SignalIntegrity）

主体 = **Touchstone / Network / Circuit / Frequency 四大主类** + `constants`。
骨架 = skrf ∩ SI 交集；旧库 rf-touchstone 功能 100% 覆盖是硬约束；单库独有功能
逐条显式批准。算法不重新发明，借鉴 skrf 已验证实现。
逐模块覆盖矩阵与延后清单见[功能覆盖规划](功能覆盖规划.md)。

## 路线图

**地基从脚手架起就是四端的。** 每个功能变更的 DoD = core 实现 +
三绑定同步暴露 + 四端测试全绿。条目按先后顺序排列。

- **脚手架** ✅：monorepo、CI 矩阵、三绑定 hello world、零拷贝往返
  （已归档：`openspec/changes/archive/2026-09-27-monorepo-scaffold/`）。
- **测试基础设施**：`testdata/` 布局、`manifest.json` 契约、
  `gen_golden.py` 最小可用版 + 首批 parse golden 进 git、`golden-refresh.yml`
  周 CI、四端 golden harness。DoD = 一个 parse 用例走通 manifest → golden →
  四端断言全链路（含"假 golden 必须失败"自检）。
- **Touchstone 核心**：Rust 流式解析（memmap2+rayon）、RI/MA/DB、
  1.0/1.1；skrf golden；三绑定同步暴露，四端 golden 全绿。
  **公开面收敛（同期）**：`Handle` 已是 `@internal`（类骨架期已兑现：数据入口
  返回实例、释放为实例 `drop()`）；本项再把 `upload` 藏进构造路径（如 `Network.fromTouchstone`/
  `fromData` 内部 upload），释放继续藏进实例 `drop()`；`upload` 的
  transfer/detach 副作用对用户仍可见，每个数据入口必须显式声明"拷进"还是
  "移进"（或显式 `{ transfer: true }` 选项）。剩余动词退役随本项 spec delta 走。
- **wasm 性能定标与提速**：wasm 单线程基准 harness；50MB s4p 往返实测，
  把[铁律六](../openspec/specs/project-governance/spec.md)的 wasm"单独定标"落成
  阈值回写；提速候选 simd128 / 分块调优 / allocator / 可选 wthreads。
  DoD = 基线进 CI benchmark job，阈值写回铁律六。
- **Network**：骨架（数据入口 + `readElement` + `drop`，三端）已随
  `unify-drop-verb-and-class-surface` 落地；本项补参数互转、级联、renumber、
  mixed-mode、passivity、FFT 时域（四端同步）。
- **Circuit**：互连求解、auto_reduce（四端同步）。
- **绑定高级能力**：GIL 精细化、Node AsyncTask、wasm 视图失效强制机制、
  CSV 导入导出、旧库迁移文档。
- **高级功能（按需逐项加）**：Calibration / Deembedding / Vector Fitting。
- **光学适配验证**：域无关 API 跑通光子学 mzi/ring 示例。
- **viewer（独立立项）**：Smith 圆图 + trace 图，只读视图渲染；发布名预留
  `@netwave/viewer`，插件 `@netwave/<功能名>`。

## 待决细节清单（各自钉入对应路线图项的 design.md）

- [ ] 插值方法全集与边界外推（超出原频率范围：拒绝/外推/NaN）——Network
- [ ] mixed-mode 端口配对约定（skrf a/b 交替 vs 分组式，影响光学平衡模式映射）——Network
- [ ] 就地改写 vs 只读视图：三端统一语义（建议：可写，文档声明"视图写回即改 core 对象"）——Network
- [ ] 奇异/病态矩阵错误语义：三端错误类型映射表（PyErr 子类 / napi Error / wasm throw）+ manifest 是否加"预期失败"用例——Network
- [ ] Python GIL：所有计算入口 `py.allow_threads`；Node 大计算入口 AsyncTask
      （async 面清单）——绑定高级能力
- [ ] wasm 视图失效的具体强制机制与测试——绑定高级能力
- [ ] 频率轴非单调/重复频点的解析与拒绝规则——Touchstone 核心
- [ ] **网络/文件 I/O 归属与异步边界（暂不决策，Touchstone 核心立项时定案）**：
      数据入口不止"内存里已有字节"——还有读本地文件、拉远程 URL（如
      `Network.fromTouchstone(pathOrUrl)`）。铁律十一（绑定薄壳）禁止把 fetch/
      文件读塞进 py/ts 壳，故 I/O MUST 在 core 实现；但 wasm 无原生网络/文件系统，
      浏览器 wasm 内任何 I/O 物理上都是 JS API 调用——core 侧唯一的"自己的
      fetch"是用 `web_sys::fetch` + `wasm_bindgen_futures` 写调用（cfg 门控到
      browser feature），编译产物仍是浏览器 fetch。故"I/O 归 core"在浏览器端的
      可实现含义 = 调用写在 core 源码里（cfg 分后端），而非"Rust 有独立网络栈"。
      待决子问题：① 各端 HTTP 客户端选型（原生端 `reqwest`/`ureq`、wasm 端
      `web_sys::fetch`）与是否引入依赖；② `fromTouchstone` 是否统一收 path 与
      URL、如何区分二者、是否另立 `fromUrl` 具名入口（三端同名同语义）；
      ③ 本地文件读走 `std::fs`/`memmap2`（同步、不占堆、按需分页，铁律六已定
      memmap2 在 core）还是异步 fs，与 URL 入口是否共用一个动词；④ core 一旦
      含 I/O 动词，「core 内部全部同步」（zero-copy-roundtrip spec）须修订为
      「计算动词同步；I/O 动词按平台异步——wasm 返回 `Promise`、node 走 napi
      AsyncTask、Python 阻塞 + `allow_threads`」，异步边界在 core 表达、壳零改动；
      ⑤ 浏览器 fetch 受同源/COOP-COEP 约束、无 `file:` scheme，URL 入口在浏览器
      与原生端能力不对称，如何对用户声明这层差异；⑥ 与 `upload`/`drop` 托管契约
      的关系——URL 拉回的字节是直接进 core 解析还是先落 `resources` 表；⑦ 三端错误
      类型映射（网络失败 / 404 / 超时 → PyErr / napi Error / wasm throw）。
      本条只登记问题，禁止在 unify-drop-verb 等无关 change 中顺带拍板。
- [ ] 三端绑定壳省力化（动词 ≥10 个时兑现，预计 Network 期）：
      ① 仓库内小生成器读动词清单生成三端 `lib.rs` wrapper 段（动词 <10 个时手写壳最省）；
      ② 一致性靠测试兜底：扩展 exports 测试与 cross_compare，断言三端导出动词集合完全相等，
      漏绑即 CI 红
