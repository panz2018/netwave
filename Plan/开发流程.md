# NetWave 开发流程

> 本文档固化 netwave 每个模块的开发循环。哲学：**上"约束"（磁盘上的铁律 + 先红后绿），
> 不上"脚手架"（多智能体编排、CLI 状态机）**。强模型够用，但补它三个结构性短板：
> 跨会话失忆、会跳测试、无法自证浮点正确。
>
> 铁律见 `constitution.md`，测试细节见《测试规划.md》，功能范围见《功能覆盖规划.md》。

## 核心循环：grill → spec → red → green → review

每个核心模块（Touchstone / Network / Circuit / Frequency 及其子功能）走同一个五步循环：

```
┌─ grill ──► spec ──► red ──► green ──► review ─┐
│  逼问需求   写契约   写失败   最小实现   两轴审查  │
│                              测试               │
└──────────────────────────────────────────────────┘
         发现设计错了？回到 spec / grill
```

### 1. grill —— 动手前逼问需求（防"做错东西"）

- 用 Harness `grill-with-docs` skill（或手写问答）把模糊点逼出来：端口范围？复数 z0 要不要支持？
  边界情况？性能目标？
- 产出：把关键决策写进当前变更文件夹的 `proposal.md` / `design.md`（见下 §2），或 `Plan/` 下一段 ADR。
- **不写代码。** 这一步只对齐"做什么、为什么"。

### 2. spec —— 写可测试契约（防"做歪"）

- 一个模块 = 一个变更文件夹（借 OpenSpec 思想，纯目录，不装 CLI）：
  ```
  Plan/changes/<module>-<slug>/
    proposal.md   # 为什么、改什么
    spec.md       # 可测试需求 + 每条的容差 + 边界（端口数、格式、异常输入）
    design.md     # 交错复数布局、算法选型（照搬 skrf 哪个函数）
    tasks.md      # 实现清单，每项可验证
  ```
- spec 里每条需求必须**可测**：写成"给定 X 输入，S→Z 输出与 skrf golden 误差 < 1e-12"这种。
- 需求含糊到会影响范围时，最多标 3 个 `[NEEDS CLARIFICATION]`，其余做合理默认。

### 3. red —— 先写失败测试（铁律二）

- 在写实现**之前**，先写测试并**运行看到它失败**：
  - L3 golden：`gen_golden.py` 用 skrf 生成期望 → 写断言读 manifest + golden 比对。
  - L1 解析自校验：λ/4 变换器、往返恒等等闭式解。
  - L2 proptest：随机 Network 的不变量。
- 期望值来自独立真值（skrf / 教科书 / 物理不变量），**绝不用被测代码算**。
- 测试没跑红过 = 不知道它测的对不对 = 不算数。

### 4. green —— 最小实现让测试通过

- 只写让当前测试通过的最小代码，不anticipate 未来需求、不顺手加没测的功能。
- 一次一个 vertical slice：一个测试 → 一段实现 → 重复。不"先写完所有测试再写完所有实现"。
- 照搬 skrf 已验证算法，不重新发明（见《功能覆盖规划.md》）。

### 5. review —— 提交前两轴审查（防"腐化"）

- 两轴并行审查（有 Harness `code-review` skill 可用它，没有就手工自查）：
  - **Standards 轴**：是否合 `constitution.md` 六条铁律？有无 Fowler 坏味道（尤其 Speculative Generality——Rust 里过度造轮子）？
  - **Spec 轴**：是否忠实实现了 spec.md？有无多做/少做？
- 跨端改动额外跑 L4 跨绑定对拍（core/python/node/wasm 同输入 bit 级一致）。
- CI 全绿（clippy -D warnings、fmt、criterion 无劣化）才允许合并。

## 何时可以简化

| 场景 | 简化 |
|---|---|
| 改文档 / 注释 / 常量 | 跳过 red/green，直接改 + review |
| 修 bug | 走完整循环，但 red 步 = 先写一个复现该 bug 的失败测试（diagnosing-bugs 先建反馈回路） |
| 一次性原型 / 探索 | 允许 throwaway，不写测试，但**代码不进主干**，结论回写 spec |
| 纯绑定胶水（无新数值逻辑） | 跳过 L1/L2，保留 L4 对拍 |

## 工具落地（全部可选，非前置条件）

> **进入编码的唯一硬前置是构建链**（`cargo` / `maturin` / `napi`，即阶段 0 脚手架本身）。
> 下列流程工具都是"锦上添花"，**随时可装、可跳过**——五步循环手写就能跑通，
> 磁盘上的 `constitution.md` + 本文档已足够开工。

| 工具 | 何时考虑 | 不装的代价 |
|---|---|---|
| mattpocock/skills | 想要更系统的 grill / review 提问清单时 | 无——我临场发挥也能跑五步；本质是几个 markdown 提示词，`npx skills add` 一条命令随时补装 |
| OpenSpec CLI | change 目录多到手工管理烦人时（阶段 2+） | 无——手工建 `Plan/changes/` 目录即可，结构与 OpenSpec 一致 |
| Comet / spec-kit / superpowers | **不装** | —— 编排对单人单 agent 是负资产；constitution 概念已抄入 |

## 为什么是这套而不是 Comet/spec-kit

- Comet 自己的评测：强模型下 Native（去掉重流程）比 Classic（完整 OpenSpec+Superpowers）
  **省 76.8% token、pass^3 更高**。它的重编排是给多智能体长任务准备的，netwave 单人单 agent 用不上。
- spec-kit 的九 Articles 是防弱模型跑偏的模板，强模型下多是空转仪式；但它发明的
  **constitution（磁盘上的不可协商铁律）** 是真值钱——已单独抄进 `constitution.md`。
- 本流程只保留两样对 netwave 风险**对症**的东西：**铁律（防跨会话漂移）+ 先红后绿（防跳测试、防自证）**。

## 一句话纪律

> **动手前 grill，写代码前 red，提交前 review，全程守 constitution。**
> 违反任何一条铁律的 PR，无论功能多完整，一律不合。
