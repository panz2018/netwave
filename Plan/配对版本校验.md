# 配对版本校验落地研究

> 研究问题：`scripts/versions.json` 的 `paired_with` 目前只校验"配对名字存在"，
> 不校验"配对双方版本是否相容"。本文逐对核实每条配对边的**真实约束语义**与
> **可机检性**，给出登记表 schema 与闸门落点建议，供拍板后开 OpenSpec change。
> 现状缺口描述见
> [测试规划·配对版本校验](测试规划.md#配对版本校验pairedwith-只校验名字存在不校验版本相容)。

## 大白话结论（先读这段）

把"这俩版本得配套"这件事交给机器查，关键不是造一个万能规则，而是**给每一对
关系声明它属于哪一种固定句式**（相等 / 不小于 / 落在某范围 / 上游说了算 / 只提
醒不硬拦）。声明好之后，闸门按声明逐条执行。难点在于：有些配对两边的数字**仓库
里就能读到**（离线可查，进 `pnpm check:meta`），有些必须**联网问上游**某个版本
支持到哪个 Python/Node（在线，进 `pnpm check:outdated`），还有些**根本没有数字
约束**（只是"升级时一起升"，硬拦反而误报）。把这三类分清楚，就是落地的全部。

## 现状：闸门到底查了什么

`scripts/check_versions.py` 对 `paired_with` 只做一件事——结构检查末尾的"悬空名
校验"：每个 `paired_with` 引用的条目名必须在登记表里存在。**不读任何版本号、不
比较任何配对**。所以 `python-runtime`(3.14) 与 `python-requires`(>=3.10) 这对，
闸门知道"它俩是一对"，但即使把 runtime 改成 3.9（低于 floor）也不会 FAIL。

更关键的隐藏缺口：`current_values()`（闸门里"从仓库文件读当前钉版值"的函数）
**只读得懂这几种值**——`rust-toolchain.toml` channel、`packageManager`、
`.python-version`、CI workflow 里的 `python-version:`/`node-version:` 矩阵格、
全 pin 的 action tag、`discovered:` 规则发现的成员 MSRV。它**读不出**
`pyproject.toml` 的 `requires-python`、`package.json` 的 `engines.node`、
`devDependencies` 里的具体版本、`Cargo.lock` 里解析出的 crate 版本。也就是说，
即便现在想加配对校验，多数配对边的"值"根本还没被抽出来。这是落地的真正前置工作，
不是写个比较函数那么简单。

## 逐对核实：每条配对边的语义与可机检性

下表把登记表里全部配对关系列全，每对标注：真实约束、约束能否离线读值、建议约束
词、由哪个闸门执行。"离线可读"指当前 `current_values()` 已能读到，"需补 reader"
指值在仓库文件里但函数还没解析，"在线"指值不在仓库（机器上装的版本 / 上游声明）。

| 配对边（A ↔ B）                                     | 真实约束语义                                                                | 值可读性                                         | 约束词     | 执行闸门                                    |
| --------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------ | ---------- | ------------------------------------------- |
| `rust-toolchain` ↔ `rust-msrv`                      | 成员 MSRV ≤ toolchain pin（major.minor）                                    | 离线可读                                         | `le`       | `check_versions.py`（已实现，仅缺登记表达） |
| `python-runtime` ↔ `python-requires`                | runtime(3.14) ≥ requires-python floor(3.10)                                 | runtime 可读 / floor 需补 reader                 | `ge`       | `check_versions.py`                         |
| `python-requires` ↔ `ci-python-matrix`              | CI 矩阵最低格 == requires-python floor                                      | 矩阵可读 / floor 需补 reader                     | `floor_eq` | `check_versions.py`                         |
| `node-engines` ↔ `ci-node-matrix`                   | CI 矩阵最低格 == engines.node floor(22)                                     | 矩阵可读 / engines 需补 reader                   | `floor_eq` | `check_versions.py`                         |
| `python-runtime` ↔ `ci-python-matrix`               | runtime ∈ 矩阵某格（现由 .python-version 泛查覆盖）                         | 离线可读                                         | `in`       | `check_versions.py`（check #5 已部分覆盖）  |
| `napi-pair` ↔ `napi-crate`                          | `@napi-rs/cli` major(3) == `napi` crate major(3)                            | 均需补 reader（devDep + Cargo.lock）             | `eq_major` | `check_versions.py`                         |
| `pyo3-numpy-pair` 内部（pyo3↔numpy）                | pyo3(0.29) 与 numpy(0.29) 同 major（升级方法已声明 same-major lockstep）    | 需补 reader（Cargo.lock）                        | `eq_major` | `check_versions.py`                         |
| `typescript-tsdown-pair` ↔ `tsdown`                 | typescript(7.0.2) 落在 tsdown 声明的 peer 范围 `^5‖^6‖^7`                   | peer 范围在 lockfile/registry，不在 package.json | `peer`     | `pnpm peers check`（见下）                  |
| vitest 全家桶 peer（未登记）                        | `@vitest/browser` 等要求 `vitest` 精确版                                    | lockfile 编码                                    | `peer`     | `pnpm peers check`                          |
| `pyo3-numpy-pair` ↔ `python-runtime`                | pyo3 0.29 支持到的 Python ≤ runtime；3.15 支持在 pyo3 0.30 才加             | 在线（上游声明）                                 | `upstream` | `check_outdated.py`                         |
| `pnpm` ↔ `node-global`                              | pnpm `engines.node >=18.*` vs 机器 node 版本                                | 在线（机器侧）                                   | `upstream` | `check_outdated.py`                         |
| `napi-pair` ↔ `node-global`                         | `@napi-rs/cli` `engines.node ^20.17‖^22.13‖>=23.5` vs 机器 node             | 在线（机器侧）                                   | `upstream` | `check_outdated.py`                         |
| `oracle-python` ↔ `python-runtime`（oracle 落地后） | oracle `.python-version` == 主工程 `.python-version`                        | 离线可读（两个 .python-version 都在仓库）        | `eq`       | `check_versions.py`                         |
| `uv-lock` ↔ `python-runtime`                        | uv.lock `requires-python >=3.10` ≤ runtime                                  | lockfile 可读                                    | `ge`       | `check_versions.py`                         |
| `wasm-pack` ↔ `binaryen`                            | 无版本约束，仅"升级时一起重跑安装脚本"                                      | 无数字                                           | `none`     | 不拦（仅登记关系）                          |
| `cargo-lock` ↔ `pyo3-numpy-pair`/`napi-crate`       | lockfile 是解析后真相，真正的相等约束由上面 `eq_major` 在 Cargo.lock 上执行 | 结构性                                           | `none`     | 不拦（advisory）                            |
| `pnpm-lock` ↔ `typescript-tsdown-pair`              | 无独立约束（peer 由 `peers check` 覆盖）                                    | 结构性                                           | `none`     | 不拦（advisory）                            |
| 各 `*-global` ↔ 其工具链 pin                        | 机器装的全局 CLI 版本 vs 项目 pin                                           | 在线（机器侧）                                   | `upstream` | `check_outdated.py`                         |

核实依据（关键几条，可复核）：

- tsdown 的 peer 范围：`pnpm-lock.yaml:2216`（`typescript: ^5.0.0 || ^6.0.0 || ^7.0.0`），
  当前 typescript 7.0.2 满足——所以这对**今天不报错**，但 package.json 里看不到
  这个范围，只能从 lockfile 或 registry 读，故归 `peer` 类而非离线 `range`。
- pyo3 对 Python 上限属上游声明：pyo3 0.30.0 CHANGELOG 才加 "Support Python
  3.15.0 final"（[PyO3 CHANGELOG](https://raw.githubusercontent.com/PyO3/pyo3/main/CHANGELOG.md)，
  PR #6517）；当前 0.29 不支持 3.15。这类"谁支持谁"无法离线算，必须联网查上游。
- `pnpm peers check` 退出码实测：peer 全满足退 0、有 unmet 退 1（`--strict` 退 2），
  且读 lockfile 不联网——是现成的、机器可读的 peer 闸门。本仓根目录当前退 0
  （`No peer dependency issues found`）。
- `uv lock --locked` 离线断言 lock 与 pyproject 一致，实测退 0——是现成的
  "uv.lock ↔ python 声明"一致性闸门，无需自造。
- pnpm `engines.node`、`@napi-rs/cli` `engines.node` 取自 npm registry 对应版本
  的 `engines` 字段（`>=18.*`、`^20.17.0 || ^22.13.0 || >= 23.5.0`）。

## 生态现成做法（先查再提，避免重造）

"声明式配对约束 + 安装器/解析器校验"是各包管理器的标准能力，netwave 不是发明新
机制，而是把同一思路用在**包管理器罩不住的跨工具钉版点**上：

- **npm/pnpm/yarn**：`peerDependencies` 声明"我要求某包在某范围"，
  `peerDependenciesMeta` 标可选；安装器校验，pnpm 另给 `peers check` 命令
  （实测退码见上）。这是 `peer` 约束词的现成原型。
- **cargo**：`[dependencies]` 的版本请求 + `Cargo.lock` 解析真相；`cargo tree -d`
  查重复版本。`eq_major`（pyo3↔numpy、napi-cli↔napi）本质是"同一 crate 树里
  major 必须一致"，cargo 解析已保证，闸门只是把"升级方法里写的 same-major"变成
  机器断言。
- **Python/PEP 440**：`requires-python` 与依赖的版本说明符；uv `--locked`/`--frozen`
  断言 lock 不漂移（实测可用）。`ge`/`floor_eq` 就是 PEP 440 说明符的子集。
- **endoflife.date / nodejs.org dist index**：`upstream` 类（谁支持到哪个版本）的
  权威数据源，`check_outdated.py` 已在用。

结论：约束词不必自造语义，每个词都对应一个成熟生态机制；netwave 的增量只是
"跨 rust-toolchain / CI 矩阵 / .python-version / lockfile 这些不同文件之间的
配对"没有现成工具，需要一张登记表 + 一个按声明执行的薄闸门。

## 为什么"固定约束词表"不等于"假通用规则"

测试规划担心"硬造一个假通用规则比不检查更糟"。这个担心是对的，但它反对的是
**用一条规则套所有配对**。本方案不这么做：约束词是一个**封闭小集合**，每个词有
精确语义，**每条边自己声明属于哪个词**——这正是 npm/cargo/PEP 的做法（声明式，
不是猜）。集合建议：

| 约束词      | 含义                              | 例子                                |
| ----------- | --------------------------------- | ----------------------------------- |
| `eq`        | 两侧版本完全相等                  | oracle-python == python-runtime     |
| `eq_major`  | 两侧 major 相等（lockstep）       | napi-cli ↔ napi、pyo3 ↔ numpy       |
| `le` / `ge` | A ≤ B / A ≥ B（数值比较）         | MSRV ≤ toolchain、runtime ≥ floor   |
| `floor_eq`  | 矩阵最低格 == 声明的底线          | CI python 最低格 == requires-python |
| `in`        | A 出现在 B 的版本集合里           | runtime ∈ CI 矩阵                   |
| `peer`      | A 落在 B 的 peerDependencies 范围 | typescript ∈ tsdown peer            |
| `upstream`  | 相容性由上游声明，联网查          | pyo3 ↔ python、pnpm ↔ node          |
| `none`      | 无数字约束，仅登记"一起升级"关系  | wasm-pack ↔ binaryen                |

每个词都有唯一确定的判定方式，闸门按词分发，没有"一条规则打天下"。误报风险由
"读不到值就跳过并明确报告跳过原因"控制，而不是靠猜。

## 登记表 schema 建议（边为一等公民）

`paired_with` 是"每条 entry 列出和我相关的名字"，但**同一 entry 的不同配对约束
不同**（`python-runtime` 对 `python-requires` 是 `ge`、对 `ci-python-matrix` 是
`in`、对 `pyo3-numpy-pair` 是 `upstream`），所以约束**不能挂在 entry 上**（测试
规划草拟的"给条目加 `constraint` 字段"在多配对时语义歧义）。建议**边独立成表**：

```jsonc
// scripts/versions.json 顶层新增（示意，最终结构由 change 定）
"pairs": [
  { "a": "rust-toolchain", "b": "rust-msrv",            "constraint": "le",       "check": "offline" },
  { "a": "python-runtime", "b": "python-requires",       "constraint": "ge",       "check": "offline" },
  { "a": "python-requires","b": "ci-python-matrix",      "constraint": "floor_eq", "check": "offline" },
  { "a": "node-engines",   "b": "ci-node-matrix",        "constraint": "floor_eq", "check": "offline" },
  { "a": "napi-pair",      "b": "napi-crate",           "constraint": "eq_major", "check": "offline" },
  { "a": "pyo3",           "b": "numpy",                "constraint": "eq_major", "check": "offline", "note": "Cargo.lock 解析版" },
  { "a": "typescript-tsdown-pair", "b": "tsdown",       "constraint": "peer",     "check": "peers" },
  { "a": "pyo3-numpy-pair","b": "python-runtime",       "constraint": "upstream", "check": "outdated" },
  { "a": "wasm-pack",      "b": "binaryen",             "constraint": "none",     "check": "none" }
]
```

要点：

- **`check` 字段标明执行者**：`offline`（进 `check_versions.py`，纯标准库、不联网）、
  `peers`（进 `pnpm peers check`）、`outdated`（进 `check_outdated.py`，联网）、
  `none`（不执行，仅登记关系）。闸门各管各的，离线闸门绝不碰在线边。
- **`paired_with` 与 `pairs` 二选一，不留两份真相**：本仓已为"第二个真相源"删过
  `sha256`/`cases[]`。建议 `pairs` 成为配对唯一真相，`paired_with` 退役或降级为
  由 `pairs` 派生的视图；若保留 `paired_with`，闸门 MUST 双向对账（每个
  `paired_with` 名出现在某条 pair、每条 pair 的两端也出现在对方 `paired_with`），
  否则就是漂移。**这是结构性变更，须走 OpenSpec change**（与测试规划
  「落地形态」判断一致）。
- **`none` 边保留**：它承载"升级方法里的一起升"语义，登记有价值，只是闸门不拦。

## 闸门落点与实施顺序（拍板后执行，非本文）

1. **补值抽取**（前置，无它则一切免谈）：给 `check_versions.py` 加 reader——
   `pyproject.toml` 的 `requires-python`、`package.json` 的 `engines.node` 与
   `devDependencies.<pkg>`、`Cargo.lock` 指定包版本、`uv.lock` 的 `requires-python`。
   每个 reader 失败时返回"读不到"而非崩，配对校验据此跳过并报告。
2. **加 `pairs` 表 + 离线分发器**：`check_versions.py` 读 `pairs`，对
   `check: offline` 的边按约束词比较两侧值；读不到任一侧 → 报告"skipped
   (value unreadable)"，不 FAIL（避免误报耗尽信任）。把现有 MSRV `le`、
   `.python-version ∈ 矩阵` 也纳入 `pairs` 表达，消除"一致性规则散落在代码里"。
3. **peer 边接 `pnpm peers check`**：在 `check:meta`（或 `check:ts`）加一步
   `pnpm peers check`，覆盖 typescript↔tsdown、vitest 全家桶等所有 peer 关系，
   零自造解析。需 lockfile 在场（CI 在 `pnpm install` 之后跑，满足）。
4. **在线边留 `check_outdated.py`**：`upstream` 边（pyo3↔python、pnpm↔node、
   各 global CLI）在联网体检里加"配对相容"段，复用其已有的 registry + blocked
   过滤，不进离线闸门。
5. **oracle 落地时**：`oracle-python ↔ python-runtime` 加一条 `eq`/`offline` 边，
   即测试规划「一致性兜底」点名的首个实例——两个 `.python-version` 都在仓库，
   离线可硬拦，从此 `paired_with` 不再是文档意图。

## 与现有契约的冲突点（须在 change 里处理）

- **`check_versions.py` 引入 pnpm 子进程？** 不建议。`peers check` 作为 `check:meta`
  的**独立一步**，而非塞进 `check_versions.py`（后者保持纯标准库、可单文件跑）。
  这样"离线纯 python 闸门"与"需要 pnpm 的 peer 闸门"职责分离，各自可独立诊断。
- **`upstream` 边依赖网络**：`check_outdated.py` 本就是"人工触发、MUST NOT 进 CI"
  （dependency-upgrade spec「过期体检命令」），`upstream` 配对校验天然继承该约束，
  不破坏"离线闸门不联网"。
- **`eq_major` 对 pyo3↔numpy 是否过强**：升级方法已写"same-major lockstep"，
  把它变断言是把口头契约门禁化（呼应 LL-068"可门禁化必落 pnpm check"）。若某次
  上游确实允许跨 major，再在该边登记例外，而非放弃校验。

## 拍板清单（需人工确认后才能 propose）

1. 约束词表（`eq/eq_major/le/ge/floor_eq/in/peer/upstream/none`）是否采纳，
   还是先只上 `eq/ge/le` 三个最小集。
2. `paired_with` 退役改 `pairs`，还是保留 `paired_with` 并双向对账。
3. `pnpm peers check` 接进 `check:meta` 还是 `check:ts`。
4. `upstream` 边是否值得做（联网、且多数靠 lockfile/uv 已隐式保证），还是只保留
   pyo3↔python 一条（升级风险最高者）。
5. 范围：本 change 只做"配对校验"，还是与「过期检查门禁化」合并为
   `add-freshness-schedule-gate`（测试规划「落地形态」原拟合并）。
