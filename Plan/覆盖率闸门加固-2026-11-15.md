# 覆盖率闸门加固延后项（2026-11-15）

状态：**待点名执行**。来源 = change `drain-stray-profraw-in-tests`：第 1、3 条
出自 design/proposal 专家增补中未纳入该 change 范围的项，第 2 条出自该 change

## 1 `check_ci.py` 增"报告 step 须同 step 含 show-env"机器校验

- 现状：`ci.yml` 里凡写 `--output-path coverage/` 的 step MUST 在同 step 内
  `eval "$(cargo llvm-cov show-env ...)"`——插桩环境变量不跨 step，漏了
  `show-env` 则该 step 的报告会读到旧 profraw 或空数据。此约束目前只有散文
  （账本 LL-091 show-env 泄漏/缺失、LL-095 输出目录未建），无机器校验。
- 目标文件：`scripts/check_ci.py`（已有"`test:*` 必须接进 ci.yml"的同族校验骨架）。
- 判据：解析 `.github/workflows/ci.yml`，凡 step 的 `run` 含
  `--output-path coverage/` 则该 `run` 内 MUST 同时含 `show-env`，否则报错。
- 验证：从 python job 的 step 删掉 `eval "$(cargo llvm-cov show-env ...)"`
  → `python3 scripts/check_ci.py` 退出码非 0；还原后转绿。

## 2 覆盖率跑完断言工作区无未忽略残留

- 现状：profraw 散落由 harness 钩子与 CI 前后步骤清除（见 change
  `drain-stray-profraw-in-tests`），但"覆盖率跑完后工作区是否还有别的
  未跟踪/未忽略产物"无断言——`.coverage`、`oracle/tmp/` 之类若被误加进
  `.gitignore` 之外，会静默污染下一次提交。
- 目标文件：`.github/workflows/ci.yml`（rust / python / node 三个插桩 job 的
  覆盖率链末尾），步骤体 `git status --porcelain` 有输出即报错。
- 待决：本地是否也加（本地工作区常有开发中的未跟踪文件，误报率高，
  建议先只上 CI）。
- 验证：`touch untracked-probe.txt` 后跑该步骤 → 退出码非 0；删除后转绿。

## 3 CI 断言 pytest 收集数（防 testpaths 配错致静默漏测）

- 现状：`python/pyproject.toml` 的 `testpaths = ["tests"]` 若指错目录，pytest 以
  退出码 5（no tests collected）失败——这一点已实测（见 change
  `drain-stray-profraw-in-tests` 完成记录组 2 的附带发现），故**目录整个不存在**
  会当场红。但另一种情形不红：`testpaths` 指向一个存在却几乎无测试的目录
  （例如误指 `python/src`），收集数从 67 掉到个位数，覆盖率仍可能达 100%
  （被测文件少 → 容易全覆盖），地板照样绿 = 静默漏测。
- 目标文件：`.github/workflows/ci.yml`（python job 的 `uv run pytest` 之前加一步
  `uv run pytest --collect-only -q`），以及根 pytest 的同族位置。
- 判据：收集数 MUST ≥ 一个下限（下限数值写进 `pyproject.toml` 或 ci.yml 单处，
  散文不复制数字），低于下限即非零退出。
- 待决：下限取值（建议取"当前收集数的一半"这类宽松值，只拦数量级错误，
  不做精确断言——精确断言会让每次加/删测试都要改 CI）。
- 验证：把 `python/pyproject.toml` 的 `testpaths` 临时改成 `["src"]` →
  该步骤退出码非 0；还原后转绿。

## 4 英文区文件出现中文即报错（LL-106 落闸门）

- 现状：语言约定（代码/配置/CI 步骤体属英文区，中文只进 `openspec/` 与 `Plan/`）
  只有 governance spec 散文，无机器校验。change `drain-stray-profraw-in-tests`
  把 profraw 清扫的报错文案写成中文共 18 行（两个 conftest、vitest 钩子、
  `ci.yml` 六处步骤体），`pnpm check` 全绿未拦住，靠人工 review 才发现。
- 目标文件：`scripts/check_comments.py`（已扫全仓源码与 `ci.yml`，加一条
  "英文区文件出现 CJK 字符即红"即可承载）。
- 判据：扫描命中的文件逐行找 CJK 统一表意文字（`\u4e00-\u9fff`），命中即报错；
  豁免 `scripts/check_*.py` 内作为被禁词模式的中文字面量（如 `STAGE_WORDS` 的
  `阶段`、`check_proposal.py` 的 `专家增补`/`无现成方案`）——这些是门禁自身的
  匹配模式，不是散文。豁免方式建议按"行内含正则字面量或赋值给大写常量"判定，
  避免整文件豁免留静默通道。
- 待决：豁免写法（行级判定 vs 显式行内标记），以及 `Plan/` 与 `openspec/`
  是否沿用 `check_comments.py` 现有豁免目录（应为是）。
- 验证：造 `zz-lang-probe.py` 写入一行中文注释 → `python3 scripts/check_comments.py`
  退出码非 0 并指名该文件；删除后转绿。反向验证：`scripts/check_md.py` 里的
  `阶段` 字面量不报错。
