# 体检提速：是否引入代码 AST/图谱工具（待研究讨论）

## 1. 问题：archive 态体检耗时长

health-check spec 的 archive 态要求「全项目存量」只读体检（五维度 + 语义考古维），
每次归档后跑一遍。本仓 544 个跟踪文件，体检靠 Explore 子代理逐维度 grep +
读文件全文，单次耗时长。研究是否装 AST/代码图谱工具提速。

## 2. 现状实测（2026-11-22）

- `graphify` 已装（`~/.local/bin/graphify`，0.9.106），本仓**未建图**
  （无 `graphify-out/`）。
- `codegraph` 未装。
- graphify 自带技能文档的判据（实证于其 SKILL.md）：「AST 抽取代码快且免费，
  但 docs/papers/images 的语义抽取逐文件跑模型，可能数分钟 + 数万 token」；
  「单次定向查询用 grep/Read 更快且免费，建图适合对同一语料反复提问、语料大或
  陌生、需要文本搜索看不到的链接、或结构性问题（社区/桥/循环依赖）」。

## 3. 按体检维度逐项判（哪些真能提速）

| 维度                  | 图谱能否提速 | 理由                                                                   |
| --------------------- | ------------ | ---------------------------------------------------------------------- |
| ①文档断言 vs 环境实测 | **否**       | 事实性断言要跑只读命令现场核（`command -v`、版本），AST 给不出环境真值 |
| ②死代码/孤儿引用计数  | **是**       | 引用图一次建、多次查「谁引用 X」，比每次全仓 grep 快；本维度是图谱甜点 |
| ③规则重复/冲突        | **部分**     | 跨文件同义条款是语义问题，AST 帮不上；图谱的社区/相似节点或可提示候选  |
| ④可门禁化 LL 未落闸门 | **否**       | 要读账本文本 + 比对 scripts/，是语义匹配非结构查询                     |
| ⑤Plan/ 过期           | **否**       | Plan 是文档，语义判断                                                  |
| 语义考古维            | **否**       | 「used to/no longer」类靠词表 + 语义，AST 无关                         |

结论：只有维度②（引用/依赖结构）是 AST/图谱的真甜点；其余多为语义或环境实测，
图谱帮不上，甚至 docs 语义抽取比 grep 更慢更贵。

## 4. 候选方案（待拍板，未实施）

- **A. 不引入**：体检维持 grep + Explore。最简，符合「最小规则原则」；慢但准确，
  且图谱对 5/6 维度无效。
- **B. 仅给维度②建代码图**：`graphify <repo> --no-viz`（只 AST 抽代码、跳过 docs
  语义抽取，快且免费）建 `graphify-out/graph.json`，体检维度②改查图；
  `--update` 增量刷新。其余维度仍 grep。需定：图谱产物是否入库（建议 gitignore，
  属可再生缓存）、刷新时机（归档前 `--update`）。
- **C. 引入 tree-sitter/ripgrep 级轻量 AST**：比 graphify 更轻，只做引用解析。
  需先查同生态成熟方案再定（AGENTS.md「方案先查现成做法」）。

倾向：**B 的裁剪版**——只对维度②用 `graphify --no-viz`（纯 AST、免费快），
其余维度不动。但需实测「建图 + 查询」总耗时是否真低于直接 grep，再拍板
（防为提速反增开销）。

## 6. 注意

- graphify 的 docs 语义抽取模式**不适合**本体检（慢、贵、且维度①④⑤要的是环境
  真值/语义判断，不是图谱链接）——若引入 MUST 限定 `--no-viz` 纯代码 AST。
- 提速是优化，不得降低体检覆盖度：五维度 + 语义考古维 MUST 仍逐项有结论。
